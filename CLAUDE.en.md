# CLAUDE.md

Instructions for Claude Code working in this repository. Write and maintain a **MkDocs documentation site** for production architecture patterns for AI agents.

## Purpose of This Project

Build and publish explanation pages for 12 categories and 59 patterns on MkDocs (Material) to GitHub Pages, **centered on decision-making (forces, degrees, tradeoffs)**. The information architecture is anchored on "decisions as the backbone, patterns as the vocabulary." See `PROJECT.md` for the overall picture, structure, and deployment steps. The source of truth for patterns is `patterns.yml`.

## Guiding Principles

- **`patterns.yml` + `decisions.yml` are the source of truth.** Patterns, forces, dials, tradeoffs, reference architectures, and decision rules must follow these files. **Do not add, rename, or renumber on your own.** When changes are needed, update the source YAML, regenerate artifacts with `python scripts/generate.py`, manually update `nav` in `mkdocs.yml`, and note this in the commit message.
- **Machine-readable artifacts are generated outputs.** `catalog.json`, `llms.txt`, `llms-core.txt`, `llms-full.txt`, each pattern's `GEN:meta` block, and the table in `pattern-index.md` are generated by `generate.py` from the source YAML. **Do not edit them directly.**
- **The exemplar is `docs/patterns/01-execution/01-request-to-job-gateway.md`.** When in doubt, match its structure, granularity, and tone.
- **The template is `templates/pattern.md`.** New pages should be based on it (`scaffold.py` has already applied it).
- Output language is **Japanese**. English notation for technical terms and pattern names may be included alongside.

## Required Structure for Pattern Pages

Each pattern must have the following headings **in this order** (same as the exemplar).

1. YAML front matter (`title` and `tags`: category name + applicable `F#`)
2. `# #{number} {title}`
3. `!!! abstract "TL;DR"` — one-sentence summary
4. `## Overview` — 2–4 sentences. What it does and where it fits
5. `!!! info "Position in Decision-Making"` — **Required**. Forces that necessitate it, involved dials/tradeoffs, link to decision flow
6. `## Design` — components and data flow. Mermaid diagram if needed
6. `## Problems Solved` — which characteristics/design pressures it addresses, "what breaks without it"
7. `## When to Use / When Not to Use` — **Both are required**. Without "when not to use," it's advertising, not a pattern
8. `## Element Technologies` — concrete implementation candidates
9. `## Tuning (Degrees)` — only when dials exist. Omit the entire section otherwise
10. `## Selection (Tradeoffs)` — only when conflicting alternatives exist. Omit the entire section otherwise
11. `## Related Patterns` — **at least one**, with relative links
12. `## References` — optional

Writing tip: Think in the flow of **characteristics → assumptions they break → structures needed → when to use / when not to use**. Write as "a levee against production breakage," not a capability showcase.

## Notation & Style Conventions

- **Length guideline**: ~250–500 words per pattern. Avoid verbose preambles and increase density.
- **Tone**: Pragmatic explanation that avoids over-assertion and makes tradeoffs explicit.
- **Avoid excessive decoration**: Use headings, bold, and bullet points only as needed. Match the exemplar's density.
- **Mermaid diagrams**: Use ```` ```mermaid ```` fences. Prefer `flowchart` / `sequenceDiagram`, keep nodes to 3–7. Don't force diagrams.
- **Admonitions**: Use Material syntax (`!!! note`, `!!! warning`, `!!! abstract`, etc.). Use `!!! abstract "TL;DR"` for the one-line summary.
- **Code blocks**: Always specify the language.
- Do not make destructive edits that remove existing content. Fill in stubs or add to existing text.

## Cross-Reference Conventions

- **Driving variables** use the `` `[F#]` `` format (e.g., `[F4]`). The full list is in `docs/foundations/forces.md`. Explicitly state them as the basis for dials or tradeoffs in the body text.
- **Other patterns in the same category**: `[#12 Blackboard](12-blackboard.md)` (relative within the same folder)
- **Patterns in other categories**: `[#44 Dual-LLM Privilege Separation](../09-security/44-dual-llm-privilege-separation.md)`
- **Links to the decision layer** (from pattern pages): `../../decisions/tuning-dials.md`, `../../decisions/tradeoffs.md`
- If a link target **does not yet exist**, first run `scaffold.py` to create a stub before linking (to avoid broken links in `--strict` builds).
- Write links as **file paths** (with `.md`). Do not use raw URLs or non-existent anchors.

## Build and Quality Gate (Required before every commit)

```bash
python scripts/generate.py   # Regenerate artifacts from source of truth
mkdocs build --strict         # Check for broken links & nav inconsistencies
```

Both must **pass with zero errors** as the completion criterion. `--strict` treats broken links, nav inconsistencies, and unreferenced files as failures.
`generate.py` is idempotent (running it twice produces no diff). It is also run in CI on every build.

`scaffold.py --check` can verify whether any pages have not yet been created.

## Definition of Done (per pattern)

- [ ] Required headings are present in order, with both "When to Use" and "When Not to Use"
- [ ] `!!! info "Position in Decision-Making"` block is present (forces, involved decisions, link to decision flow)
- [ ] `Related Patterns` has at least one valid relative link
- [ ] If applicable, `Tuning`/`Selection` sections include `[F#]` and links to the decision layer
- [ ] Front matter `tags` include the category name and applicable `F#`
- [ ] `patterns.yml` has `related`, `when_to_use`, `when_not`, `element_tech`, `dials`, `tradeoffs` filled in
- [ ] `<!-- BEGIN:GEN:meta --><!-- END:GEN:meta -->` markers are present (`generate.py` injects meta blocks)
- [ ] `python scripts/generate.py && mkdocs build --strict` passes without errors
- [ ] The page is registered in `nav` in `mkdocs.yml` (manually add scaffold-generated pages to nav)

## Prohibited Actions

- Altering pattern numbers or slugs, creating patterns outside of `patterns.yml`
- Editing or committing `site/` (generated output)
- **Long verbatim copies** from external articles or books (summarize in your own words; cite sources under `References`)
- Making definitive claims about uncertain product specs, version numbers, or pricing (generalize or cite sources)
- Bundling multiple patterns in a single commit (one pattern = one commit as a rule)

## Standard Workflow

1. Run `python scripts/scaffold.py` to confirm the target stub exists (generate it if missing).
2. Write the target `.md` following the template/exemplar. Reflect `tagline` and `forces` from `patterns.yml`.
3. Fill in `related`, `when_to_use`, `when_not`, `element_tech`, `dials`, `tradeoffs` in `patterns.yml`.
4. Add relative links to related patterns and the decision layer (generate stubs first if link targets are missing).
5. Run `python scripts/generate.py` to inject meta blocks and update artifacts.
6. Run `mkdocs build --strict` and resolve any errors.
7. Verify nav registration and record as one pattern = one commit.

## Agent Integration Rules

- **`AGENTS.md`** (repository root) and **`docs/agent-guide.md`** (published on the site) must be kept consistent with each other.
- **`docs/agent-proposal-template.md`** defines the agent output format. When modified, also update `AGENTS.md`.
- **MCP server** (`mcp-server/server.py`) reads `catalog.json`. Since `catalog.json` is generated by `generate.py`, there is normally no need to edit the MCP server directly.
- **Version** is tracked in the `version` field of `patterns.yml` / `decisions.yml`. Update `CHANGELOG.md` when making changes.
