# CLAUDE.md

Instructions for Claude Code working on this repository. Write and maintain the **MkDocs documentation site** for AI Agent Production Architecture Patterns.

## Purpose of This Project

Build and publish, via MkDocs (Material) on GitHub Pages, explanation pages for 59 patterns across 12 categories, **centered on decision-making (forces, dials, and tradeoffs)**. The IA backbone is "decisions as spine, patterns as vocabulary." See `PROJECT.md` for overall structure, composition, and deployment; `patterns.yml` is the single source of truth for patterns.

## Core Principles

- **`patterns.yml` + `decisions.yml` are the source of truth.** Patterns, forces, dials, tradeoffs, reference architectures, and decision rules follow these files. **Do not add, rename, or renumber on your own.** When changes are needed, update the source YAML, regenerate artifacts with `python scripts/generate.py`, manually align `mkdocs.yml`'s `nav`, and note it in the commit message.
- **`anti-patterns.yml` is also a source of truth.** Anti-pattern symptoms, root causes, and preventive patterns follow this file.
- **Machine-readable artifacts are generated.** `catalog.json`, `llms.txt`, `llms-core.txt`, `llms-full.txt`, each pattern's `GEN:meta` block, and the `pattern-index.md` table are generated by `generate.py` from the source YAML. **Do not edit them directly.**
- **The exemplar is `docs/patterns/01-execution/01-request-to-job-gateway.md`.** When in doubt, match its structure, granularity, and tone.
- **The template is `templates/pattern.md`.** New pages should be based on this (`scaffold.py` applies it automatically).
- Output language is **Japanese**. English terms and pattern names may be included alongside.

## Required Structure for Pattern Pages

Each pattern must have the following headings **in this order** (same as the exemplar):

1. YAML frontmatter (`title` and `tags`: category name + applicable `F#`)
2. `# #{number} {title}`
3. `!!! abstract "一言"` — one-sentence TL;DR
4. `## 概要` — 2–4 sentences. What it does and where it sits
5. `!!! info "意思決定上の位置づけ"` — **required**. Forces involved, relevant dials/tradeoffs, link to decision flow
6. `## 設計` — components and data flow; mermaid diagram if helpful
6. `## 解決する課題` — which characteristics / design pressures it addresses; "what breaks without it"
7. `## 向き / 不向き` — **both required**. A pattern without "when not to use" is advertising, not engineering
8. `## 要素技術` — concrete implementation candidates
9. `## 調整（程度）` — only if dials apply; otherwise omit the entire section
10. `## 選定（相反）` — only if tradeoffs apply; otherwise omit the entire section
11. `## 関連パターン` — **at least one**, with relative links
12. `## 参考` — optional

Writing tip: think in the flow **characteristic → broken assumption → required structure → when / when not**. Write as "a levee against what breaks in production," not as a feature pitch.

## Notation & Style Rules

- **Target length**: ~250–500 words per pattern. Avoid verbose preambles; maximize density.
- **Tone**: Practical, tradeoff-explicit, not overly assertive.
- **Avoid excess decoration**: Use headings, bold, and bullet points only when necessary. Match the exemplar's density.
- **Mermaid diagrams**: Use ` ```mermaid ` fences. Stick to `flowchart` / `sequenceDiagram`; keep nodes to 3–7. Don't force diagrams where they don't add value.
- **Admonitions**: Use Material notation (`!!! note`, `!!! warning`, `!!! abstract`, etc.). One-line TL;DR uses `!!! abstract "一言"`.
- **Code blocks**: Always include the language identifier.
- Do not make destructive edits that delete existing content. Fill in stubs / extend existing text.

## Cross-Reference Rules

- **Driving variables**: Use `` `[F#]` `` notation (e.g., `[F4]`). The full list is in `docs/foundations/forces.md`. Reference these in text as the rationale for dial settings or tradeoff choices.
- **Same-category patterns**: `[#12 Blackboard](12-blackboard.md)` (same-folder relative)
- **Cross-category patterns**: `[#44 Dual-LLM Privilege Separation](../09-security/44-dual-llm-privilege-separation.md)`
- **Links to decision layer** (from pattern pages): `../../decisions/tuning-dials.md`, `../../decisions/tradeoffs.md`
- If the link target **doesn't exist yet**, run `scaffold.py` first to create a stub before linking (to avoid `--strict` build failures from broken links).
- Write links as **file paths** (with `.md`). Don't use raw URLs or non-existent anchors.

## Build & Quality Gate (before every commit)

```bash
python scripts/generate.py        # Regenerate artifacts from source YAML
mkdocs build --strict              # Check for broken links / nav mismatches
python scripts/generate.py --lint  # Structural validation of pattern pages
```

All three must **pass with zero errors** before a commit is considered complete. `--strict` fails on broken links, nav mismatches, and unreferenced files.
`generate.py` is idempotent (running it twice produces no diff). CI also runs it on every push.

`scaffold.py --check` can verify whether any pages are missing.

## Definition of Done (per pattern)

- [ ] Required headings are present in order; both `向き` and `不向き` exist
- [ ] `!!! info "意思決定上の位置づけ"` block is present (forces, relevant decisions, link to decision flow)
- [ ] `関連パターン` has at least one valid relative link
- [ ] If applicable, `調整`/`選定` sections reference `[F#]` and link to the decision layer
- [ ] Frontmatter `tags` include the category name and applicable `F#`
- [ ] `patterns.yml` has `related`, `when_to_use`, `when_not`, `element_tech`, `dials`, `tradeoffs` filled in
- [ ] `patterns.yml` has `selection_criteria`, `summary_plain`, `prevents_anti_patterns` filled in
- [ ] `<!-- BEGIN:GEN:meta --><!-- END:GEN:meta -->` marker is present (`generate.py` injects the meta block)
- [ ] `python scripts/generate.py && mkdocs build --strict` passes without errors
- [ ] The page is registered in `mkdocs.yml`'s `nav` (scaffold-generated pages need manual nav addition)

## Forbidden Actions

- Changing pattern numbers or slugs; creating patterns outside `patterns.yml`
- Editing or committing `site/` (build output)
- **Copying long passages** from external articles or books (summarize in your own words; cite sources under `参考`)
- Making definitive claims about uncertain product specs, version numbers, or pricing (generalize or provide a source)
- Mixing multiple patterns in a single commit (one pattern = one commit)

## Standard Workflow

1. Run `python scripts/scaffold.py` to ensure the target stub exists (generate if missing).
2. Write the target `.md` following the template / exemplar. Reflect `patterns.yml`'s `tagline` and `forces`.
3. Fill in `related`, `when_to_use`, `when_not`, `element_tech`, `dials`, `tradeoffs` in `patterns.yml`.
4. Add relative links to related patterns and the decision layer (generate stubs first if link targets don't exist).
5. Run `python scripts/generate.py` to inject meta blocks and update artifacts.
6. Run `mkdocs build --strict` and resolve any errors.
7. Verify `nav` registration and commit as one pattern = one commit.

## Agent Integration Rules

- **`AGENTS.md`** (repo root) and **`docs/agent-guide.md`** (published on site) must stay consistent with each other.
- **`docs/agent-proposal-template.md`** is the output format for agents. When changed, update `AGENTS.md` accordingly.
- **MCP server** (`mcp-server/server.py`) reads `catalog.json`. Since `catalog.json` is generated by `generate.py`, there is normally no need to edit the MCP server directly.
- **Versioning** uses the `version` field in `patterns.yml` / `decisions.yml`. Update `CHANGELOG.md` when changing the version.
