# 意思決定記録（ADR）テンプレート

!!! abstract "一言"
    設計判断の「なぜ」を再現可能な形で残します。フォース評価・二者択一・ダイヤル設定の根拠を1枚に。

## ADR とは

「なぜタイムアウトを5秒にしたのか」「なぜ非同期を選んだのか」——半年後にこう聞かれて即答できるでしょうか。Architecture Decision Record（ADR）は、設計上の判断とその根拠を記録するドキュメントです。AIエージェントのアーキテクチャでは、パターンの選定だけでなく、**程度（ダイヤル）の設定値**と**相反（二者択一）の選択理由**を残すことがとくに重要です。根拠のない設定のままだと、問題が起きたときにチューニングができず、属人化にもつながってしまいます。

## テンプレート

以下をコピーして使ってください。各項目は [意思決定の進め方](decision-flow.md) のステップに対応しています。

```markdown
# ADR-NNN: [タイトル]

- **日付**: YYYY-MM-DD
- **ステータス**: 提案 / 承認 / 却下 / 廃止
- **関係者**: [決定者・レビュアー]

## 文脈

[どのシステム・機能で、何を決める必要があったか。1〜3文。]

## フォース評価（F1–F9）

| フォース | 評価 | 根拠 |
|---------|------|------|
| F1 可逆性 | 高/中/低 | [なぜその評価か] |
| F2 失敗コスト | 高/中/低 | |
| F3 1リクエストの価値 | 高/中/低 | |
| F4 レイテンシ予算 | 高/中/低 | |
| F5 入力の信頼度 | 高/中/低 | |
| F6 タスクの変動性 | 高/中/低 | |
| F7 コスト感度 | 高/中/低 | |
| F8 説明責任 | 高/中/低 | |
| F9 プロバイダ信頼度 | 高/中/低 | |

## 検討した二者択一

| 二者択一 | 選択 | 効いたフォース | 理由 |
|---------|------|--------------|------|
| [例: 同期↔非同期] | [非同期] | F4 | [処理に30秒以上かかるため] |

→ 二者択一の詳細は [相反カタログ](tradeoffs.md) を参照。

## 設定したダイヤル

| ダイヤル | 設定値 | 効いたフォース | 理由 |
|---------|--------|--------------|------|
| [例: タイムアウト] | [5分] | F4 | [最長処理時間の実測値 + マージン] |

→ ダイヤルの詳細は [程度カタログ](tuning-dials.md) を参照。

## 決定

[採用したパターン構成と、その組み合わせの理由。]

## 不採用案

[検討したが採用しなかった案と、その理由。]

## 再評価条件

[どのフォースがどう変わったら、この決定を見直すか。]
```

## 使い方のコツ

- **全フォースを埋める必要はありません**。効いたフォースだけ根拠を書けば十分です。ただし、効かなかったフォースも「低」と明記しておくと、再評価時に役立ちます。
- **ADR は意思決定の進め方の⑤に対応します**。[意思決定の進め方](decision-flow.md) の①〜④を辿った結果を、ここに記録します。
- **再評価条件がいちばん重要です**。フォースは変動するので、「F7 が高に変わったら」「月間 QPS が 10倍を超えたら」のように具体的に書いておきましょう。
- 記録の粒度は「後で同じ判断を再現できるか」を基準にします。チームの新メンバーがこの ADR を読んで、なぜこの構成になったかを理解できれば十分です。
