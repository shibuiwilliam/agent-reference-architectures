# タイムアウト（1リクエスト）

!!! abstract "一言"
    1リクエストに許す最大待ち時間を決め、コネクション占有と途中打ち切りの間でバランスを取ります。

## 概要

ある日突然、エージェントの応答が返ってこなくなり、調べてみるとロードバランサのタイムアウトで処理が途中で切断されていた——こうしたトラブルは本番環境では日常茶飯事です。

このダイヤルは、1リクエストに対してどれだけの待ち時間を許すかを制御します。同期APIと非同期ジョブでは桁が異なるので、経路ごとに設定が必要です。短すぎれば正常な処理まで中断してしまい、長すぎればコネクションプールやスレッドを占有してシステム全体が詰まります。

## なぜ調整が必要か

フレームワークの30秒やインフラの60秒といったデフォルト値は、LLM呼び出しを含むエージェント処理には短すぎることがほとんどです。かといって無制限に伸ばすと、ロードバランサ配下のコネクションが枯渇して後続リクエストが全滅します。「正常系の95パーセンタイル＋余裕」を基準に設定しておかないと、散発的なタイムアウトエラーか、リソース枯渇か、どちらかに倒れることになります。

## 値域の両端

### 小さすぎると

LLMの推論やツール呼び出しが完了する前にリクエストが打ち切られてしまいます。ユーザーにはエラーが返り、サーバー側では途中まで消費したトークンが無駄になります。リトライが重なれば負荷がさらに増す悪循環に陥ります。

### 大きすぎると

1リクエストがコネクションを長時間占有し、同時接続数の上限に達してしまいます。障害時にはスロークエリが滞留してバックプレッシャーが効かず、システム全体がハングします。クライアント側でもUIがフリーズしたように見え、ユーザー体験が大きく損なわれます。

## 決め手となるフォース

- `[F4]` レイテンシ予算 — ユーザーの待機耐性が短いほどタイムアウトも短く設定する必要があるが、エージェント処理の実時間との乖離が大きいと成功率が下がる

## 目安（出発点）

- 同期API: 5〜10秒（ストリーミング開始までの時間）
- 非同期ジョブ: 5〜30分（タスク複雑度に応じて）
- ゲートウェイ層: クライアント向けタイムアウト < バックエンド向けタイムアウト（マージンを持たせる）
- LLM API呼び出し単体: 30〜120秒（モデル・プロンプト長による）

## 調整の実務

- 本番のレイテンシ分布（p50/p95/p99）を計測し、p99＋20%をタイムアウト初期値とする
- 同期経路で収まらない場合は非同期昇格パターンを検討し、タイムアウトを二段構えにする
- タイムアウト発生率をアラート対象にし、閾値を超えたら値の見直しか処理の分割を行う
- ロードバランサ・API Gateway・アプリケーション各層のタイムアウトを揃え、不整合によるゾンビリクエストを防ぐ
