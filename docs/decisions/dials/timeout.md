# タイムアウト（1リクエスト）

!!! abstract "一言"
    1リクエストに許す最大待ち時間を決め、コネクション占有と途中打ち切りの間でバランスを取る。

## 概要

エージェントへのリクエストがどれだけの時間レスポンスを待つかを制御するダイヤル。同期APIと非同期ジョブでは桁が異なるため、経路ごとに設定が必要になる。短すぎれば正常処理が中断し、長すぎればコネクションプールやスレッドを占有してシステム全体が詰まる。

## なぜ調整が必要か

デフォルト値（フレームワークの30秒やインフラの60秒）は、LLM呼び出しを含むエージェント処理には短すぎることが多い。一方、無制限に伸ばすとロードバランサ配下のコネクションが枯渇し、後続リクエストが全滅する。本番では「正常系の95パーセンタイル＋余裕」を基準に設定しないと、散発的なタイムアウトエラーか、リソース枯渇かのどちらかに倒れる。

## 値域の両端

### 小さすぎると

LLMの推論やツール呼び出しが完了する前にリクエストが打ち切られる。ユーザーにはエラーが返り、サーバー側では途中まで消費したトークンが無駄になる。リトライが重なると負荷がさらに増す悪循環に陥る。

### 大きすぎると

1リクエストがコネクションを長時間占有し、同時接続数の上限に達する。障害時にはスロークエリが滞留してバックプレッシャーが効かず、システム全体がハングする。クライアント側もUIがフリーズしたように見え、ユーザー体験が大きく劣化する。

## 決め手となるフォース

- `[F4]` レイテンシ予算 — ユーザーの待機耐性が短いほどタイムアウトも短く設定する必要があるが、エージェント処理の実時間との乖離が大きいと成功率が下がる

## 目安（出発点）

- 同期API: 5〜10秒（ストリーミング開始までの時間）
- 非同期ジョブ: 5〜30分（タスク複雑度に応じて）
- ゲートウェイ層: クライアント向けタイムアウト < バックエンド向けタイムアウト（マージンを持たせる）
- LLM API呼び出し単体: 30〜120秒（モデル・プロンプト長による）

## 調整の実務

- 本番のレイテンシ分布（p50/p95/p99）を計測し、p99＋20%をタイムアウト初期値とする
- 同期経路で収まらない場合は非同期昇格パターンを検討し、タイムアウトを二段構えにする
- タイムアウト発生率をアラート対象にし、閾値を超えたら値の見直しか処理の分割を行う
- ロードバランサ・API Gateway・アプリケーション各層のタイムアウトを揃え、不整合によるゾンビリクエストを防ぐ
