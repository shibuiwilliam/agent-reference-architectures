# キャッシュ類似度閾値

!!! abstract "一言"
    セマンティックキャッシュのヒット判定閾値を制御し、キャッシュ効率と回答の正確性を天秤にかけます。

## 概要

「今日の為替レートは？」と聞いたのに、昨日キャッシュされた古いレートが返ってきた——セマンティックキャッシュは強力なコスト削減策ですが、類似度の判定を間違えるとユーザーの信頼を一瞬で失います。

このダイヤルは、意味的に類似したクエリに対してキャッシュ済みの結果を返すかどうかを決める類似度閾値を制御します。コサイン類似度などの距離指標で測定し、閾値以上なら過去の結果を再利用します。閾値が低いほどヒット率は上がりますがミスマッチのリスクが増え、高いほど正確ですがキャッシュの恩恵が薄れます。

## なぜ調整が必要か

LLM呼び出しはコストもレイテンシも大きいため、キャッシュの効果は高いです。しかし自然言語クエリは表現の揺れが大きく、「同じ意図」かどうかの判定が難しいのが実情です。閾値が不適切だと微妙に異なる質問に古い回答を返してしまい、ユーザーの信頼を損ないます。逆に厳しすぎるとヒット率が数%に留まり、キャッシュ基盤のコストだけが残ります。

## 値域の両端

### 小さすぎると

ほぼ完全一致のクエリしかキャッシュヒットせず、ヒット率が極めて低くなります。キャッシュインフラ（ベクトルDB・埋め込み計算）のコストに見合う効果が得られません。自然言語の表現揺れも吸収できません。

### 大きすぎると

意味が微妙に異なるクエリに対して古い結果を返してしまいます。ユーザーが「昨日の情報」や「別のコンテキスト」を期待しているのにキャッシュが返ることになります。特に時間依存性のある情報や、パーソナライズが必要なクエリで問題が表面化します。

## 決め手となるフォース

- `[F7]` コスト感度・スケール — コスト圧力が高いほどキャッシュヒット率を上げたくなるが、品質とのトレードオフが発生する

## 目安（出発点）

- コサイン類似度: 0.92〜0.97
- 事実検索系（FAQ・ドキュメント検索）: 0.95前後
- 創作・パーソナライズ系: キャッシュ自体を無効化するか、0.98以上
- 時間依存情報: TTLとの組み合わせで鮮度を担保
- 埋め込みモデル変更時は閾値の再校正が必須

## 調整の実務

- ヒット率、ミスマッチ率（ユーザーが再質問した割合）を週次で計測する
- キャッシュヒット時とミス時のユーザー満足度を比較し、閾値の妥当性を評価する
- ドメインごとに閾値を分け、一律設定を避ける
- 埋め込みモデルの更新やクエリ分布の変化に応じて閾値を定期的に再校正する
