# キャッシュ類似度閾値

!!! abstract "一言"
    セマンティックキャッシュのヒット判定閾値を制御し、キャッシュ効率と回答の正確性を天秤にかける。

## 概要

「今日の為替レートは？」と聞いたのに、昨日キャッシュされた古いレートが返ってきた——セマンティックキャッシュは強力なコスト削減策だが、類似度の判定を間違えると、ユーザーの信頼を一瞬で失う。

このダイヤルは、意味的に類似したクエリに対してキャッシュ済みの結果を返すかどうかを決める類似度閾値を制御する。コサイン類似度やその他の距離指標で測定し、閾値以上なら過去の結果を再利用する。閾値が低いほどヒット率は上がるがミスマッチのリスクが増え、高いほど正確だがキャッシュの恩恵が薄れる。

## なぜ調整が必要か

LLM呼び出しはコストとレイテンシの両方が大きいため、キャッシュの効果は高い。しかし自然言語クエリは表現の揺れが大きく、「同じ意図」の判定が難しい。閾値が不適切だと、微妙に異なる質問に古い回答を返してしまい、ユーザーの信頼を損なう。逆に厳しすぎるとヒット率が数%に留まり、キャッシュ基盤のコストだけが残る。

## 値域の両端

### 小さすぎると

ほぼ完全一致のクエリしかキャッシュヒットせず、ヒット率が極めて低い。キャッシュインフラ（ベクトルDB・埋め込み計算）のコストに見合う効果が得られない。自然言語の表現揺れを吸収できない。

### 大きすぎると

意味が微妙に異なるクエリに対して古い結果を返す。ユーザーが「昨日の情報」「別のコンテキスト」を期待しているのにキャッシュが返る。特に時間依存性のある情報や、パーソナライズが必要なクエリで問題が顕在化する。

## 決め手となるフォース

- `[F7]` コスト感度・スケール — コスト圧力が高いほどキャッシュヒット率を上げたくなるが、品質とのトレードオフが発生する

## 目安（出発点）

- コサイン類似度: 0.92〜0.97
- 事実検索系（FAQ・ドキュメント検索）: 0.95前後
- 創作・パーソナライズ系: キャッシュ自体を無効化するか、0.98以上
- 時間依存情報: TTLとの組み合わせで鮮度を担保
- 埋め込みモデル変更時は閾値の再校正が必須

## 調整の実務

- ヒット率、ミスマッチ率（ユーザーが再質問した割合）を週次で計測する
- キャッシュヒット時とミス時のユーザー満足度を比較し、閾値の妥当性を評価する
- ドメインごとに閾値を分け、一律設定を避ける
- 埋め込みモデルの更新やクエリ分布の変化に応じて閾値を定期的に再校正する
