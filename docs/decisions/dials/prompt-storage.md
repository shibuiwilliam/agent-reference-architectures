# プロンプト保存先・粒度

!!! abstract "一言"
    プロンプトのバージョン管理の粒度と保存方式を制御し、変更追跡とリポジトリ管理の負荷を天秤にかける。

## 概要

「先週まで問題なく動いていたのに、急に回答品質が落ちた」——調べてみると、誰かがプロンプトを修正していたが、変更履歴が残っていなかった。プロンプトはエージェントの挙動を決める最も影響の大きい設定であり、その管理の仕方がチームの生産性と品質を左右する。

このダイヤルは、エージェントのシステムプロンプト・テンプレート・Few-shot例をどこに・どの粒度で保存するかを決める。Gitリポジトリでコードと同列に管理する方式から、専用のプロンプトレジストリに外出しする方式まで幅がある。粒度はプロンプト全体を1ファイルとするか、セクション単位で分割するかに関わる。

## なぜ調整が必要か

プロンプトはエージェントの挙動を決定する最も影響の大きい設定だが、コードと異なりdiffが読みにくく、変更の影響を事前に予測しにくい。バージョン管理なしでは「いつ・誰が・何を変えたか」が追跡できず、品質劣化の原因調査が不可能になる。一方、過度に細かい粒度管理はリポジトリの肥大化と管理コストの増大を招く。

## 値域の両端

### 小さすぎると

プロンプトの変更履歴が残らず、回帰の原因調査が困難になる。「先週まで動いていたのに」という問題に対応できない。チーム内でプロンプトの同期が取れず、環境ごとに異なるプロンプトが動く事態が起きる。

### 大きすぎると

プロンプトの微細な修正でも大量のファイル変更が発生し、レビュー負荷が増大する。リポジトリサイズが膨らみ、CI/CDパイプラインが遅くなる。プロンプトレジストリを別途運用する場合はインフラコストも加わる。

## 決め手となるフォース

- `[F8]` 説明責任・規制 — 監査要件がプロンプト変更の追跡可能性を要求する度合い

## 目安（出発点）

- 基本方針: Gitリポジトリで管理し、バージョンタグを付ける
- 粒度: 1エージェント=1ファイル（セクション分割は共有部品がある場合のみ）
- タグ形式: セマンティックバージョニング（`prompt-v1.2.0`）
- デプロイ時にプロンプトバージョンをメタデータとして記録し、トレースと紐づける
- Few-shot例はプロンプトとは別ファイルで管理し、独立に更新できるようにする

## 調整の実務

- プロンプト変更時は評価CI/CDで品質への影響を自動テストする
- 変更理由をコミットメッセージに明記し、レビュープロセスを設ける
- プロンプトのデプロイをコードのデプロイとは独立にロールバック可能にする
- 環境間（開発・ステージング・本番）のプロンプト差分を定期的にチェックする
