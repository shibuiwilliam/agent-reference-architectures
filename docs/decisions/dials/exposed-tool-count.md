# 露出ツール数

!!! abstract "一言"
    1セッションでエージェントに見せるツール数を制御し、能力の幅と選択精度のバランスを取ります。

## 概要

「メール送信」を頼んだのに「チャット送信」ツールが呼ばれてしまった——ツールを30個も並べていれば、LLMが迷うのは当然です。しかし必要なツールを削りすぎれば、今度はタスクを完了できません。

このダイヤルは、エージェントのシステムプロンプトに含めるツール定義の数を決めます。ツールが多いほどエージェントの行動範囲が広がるが、LLMがツールを誤選択する確率も上がります。セッションの目的に応じて動的にツールセットを絞り込む設計が求められます。

## なぜ調整が必要か

LLMはツール定義をコンテキストとして受け取るため、ツール数が増えるとコンテキスト消費が増え、各ツールの説明への注意力が分散します。実験的に、ツール数が20を超えると誤選択率が有意に上がることが報告されています。一方、必要なツールが使えないとタスクを完了できません。

## 値域の両端

### 小さすぎると

タスク遂行に必要なツールが使えず、エージェントが「そのツールは利用できません」と回答するか、不適切なツールで代用しようとします。ユーザーのリクエストに応えられない場面が増え、有用性が低下します。

### 大きすぎると

類似したツール間で誤選択が頻発します。たとえば「メール送信」と「チャット送信」を取り違えます。ツール定義がコンテキスト窓を圧迫し、本来の指示やユーザー入力に使える領域が減ります。トークンコストも増加します。

## 決め手となるフォース

- `[F6]` タスクの変動性 — 定型タスクは少数のツールで済み、探索的タスクは多くのツールが必要

## 目安（出発点）

- 1セッションあたり: 5〜15個
- 定型タスク: 3〜5個に絞る
- 汎用アシスタント: 10〜15個を上限とし、カテゴリで分類
- 15個超が必要な場合: ツール選択を2段階（カテゴリ選択→ツール選択）にする
- ツール定義は簡潔に保ち、1ツールあたりのトークン消費を最小化する

## 調整の実務

- ツール利用ログを分析し、セッション種別ごとに実際に使われるツールセットを特定する
- 未使用率の高いツールをデフォルトセットから除外し、必要時にのみ追加する
- ツール誤選択率をモニタリングし、増加したらツール数の削減や説明の改善を行う
- ツール名・説明の類似性が高いペアを特定し、統合または名前の差別化を行う
