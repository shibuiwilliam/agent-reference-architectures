# リトライ回数（ネットワーク）

!!! abstract "一言"
    一時障害からの自動復旧と、リトライストームによる障害拡大の間を制御します。

## 概要

LLM APIを呼び出したら503が返ってきた。もう一度試したら成功した——こうした一時的な障害は日常茶飯事ですが、リトライの仕組みがなければ毎回ユーザーにエラーが見えてしまいます。

このダイヤルは、LLM APIやツール呼び出しがネットワーク障害・レート制限で失敗したときに、何回まで自動再試行するかを決めます。回数だけでなく、バックオフ戦略（指数・ジッター）もセットで設計します。外部プロバイダの可用性に依存するエージェントでは、最初に調整すべき項目の一つです。

## なぜ調整が必要か

LLM APIは429（レート制限）や503（過負荷）を頻繁に返します。リトライなしだと一時障害がそのままユーザーのエラーになってしまいます。しかしリトライ回数を増やしすぎると、障害時に全クライアントが同時再試行して、回復しかけたサービスを再び潰す「リトライストーム」が発生します。

## 値域の両端

### 小さすぎると

一時的な503やネットワークタイムアウトで即座に失敗が確定します。LLMプロバイダの瞬断は珍しくなく、リトライ0回では体感エラー率が数%に達することもあります。ユーザーの信頼を損ない、手動リトライがさらに負荷を増やします。

### 大きすぎると

障害が長引く場面でリクエストが滞留し、コスト（トークン再消費）とレイテンシが膨張します。同一リクエストの多重実行によって、冪等でないツール呼び出しが副作用を重複させるリスクもあります。バックオフなしの即時リトライは特に危険です。

## 決め手となるフォース

- `[F9]` プロバイダ信頼度 — 外部LLMの可用性が低いほどリトライの必要性は高まるが、同時にストームリスクも上がる

## 目安（出発点）

- 基本: 2〜3回（指数バックオフ＋ジッター付き）
- 初回バックオフ: 1〜2秒、最大30〜60秒
- 429応答: `Retry-After` ヘッダを尊重
- 冪等でない操作: リトライ前に状態確認を挟む、またはリトライしない

## 調整の実務

- リトライ込みの成功率と、リトライによる追加コスト・レイテンシをダッシュボードで可視化する
- サーキットブレーカーと組み合わせ、連続失敗が閾値を超えたらリトライ自体を停止する
- マルチプロバイダ構成では、同一プロバイダへのリトライよりフォールバック切替を優先する
- 負荷試験で意図的に障害を注入し、リトライストームが発生しないことを確認する
