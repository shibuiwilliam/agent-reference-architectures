# メモリ TTL

!!! abstract "一言"
    エージェントの記憶に有効期限を設け、情報鮮度の維持とコンプライアンスを両立する。

## 概要

エージェントが保持する各種メモリ（セッション履歴・ユーザープリファレンス・学習結果）の生存期間（Time To Live）。TTLが短いと有用な記憶が早期に失われ、長いと古い情報に基づく誤判断やデータ保持規制への抵触が生じる。メモリ種別ごとに異なるTTLを設定するのが基本。

## なぜ調整が必要か

エージェントの記憶は時間とともに陳腐化する。顧客の好み、社内ポリシー、技術仕様は変わるため、古い記憶に依存すると誤った判断を下す。一方、GDPR等のデータ保護規制は不要なデータの削除を求める。TTLなしでは記憶が際限なく増加し、検索精度の低下とストレージコストの増大も招く。

## 値域の両端

### 小さすぎると

ユーザーが先ほど伝えた好みや指示を忘れ、同じ質問を繰り返す。過去の失敗から学んだ知見も消え、同じミスを再発する。セッション内の連続性が失われ、対話体験が劣化する。

### 大きすぎると

変更された事実（退職した担当者、廃止されたAPI、更新されたポリシー）に基づいて行動する。個人データの不要な長期保持が規制違反になるリスクがある。メモリストアが肥大化し、検索のノイズが増える。

## 決め手となるフォース

- `[F8]` 説明責任・規制 — データ保持に関する規制要件がTTLの上限を決める

## 目安（出発点）

- セッションメモリ: 1〜24時間（対話終了後に破棄）
- ユーザープリファレンス: 30〜90日（定期的な再確認を推奨）
- 学習済みパターン: 90〜365日（評価で有効性を検証してから延長）
- 個人データ: 法規制の要求する期間を上限とする
- TTL切れの記憶は要約に圧縮して保持する選択肢もある

## 調整の実務

- メモリ種別ごとにTTLポリシーを定義し、自動削除ジョブを設定する
- TTL切れ直前の記憶をサンプリングし、まだ有用なものの割合を測定する
- ユーザーから「忘れている」というフィードバックが増えたらTTL延長を検討する
- データ保護責任者と連携し、規制要件の変更にTTLを追従させる
