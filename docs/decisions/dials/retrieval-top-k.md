# 検索 top-k / 投入量

!!! abstract "一言"
    RAGで取得するチャンク数を制御し、情報の網羅性とコンテキスト溢れのバランスを取ります。

## 概要

RAGで回答を生成したものの、肝心の根拠となる文書がコンテキストに含まれておらず、ハルシネーション混じりの回答が出てしまった。一方、チャンクを大量に投入したら無関係な情報にLLMが引きずられた——取得件数の多寡はRAGの品質を直接左右します。

このダイヤルは、検索拡張生成（RAG）において、ベクトル検索やハイブリッド検索から取得する上位k件のチャンク数を決めます。kが大きいほど関連情報を取りこぼす確率は下がりますが、LLMに投入するコンテキストが膨らみ、トークンコスト増加・注意の希薄化・レイテンシ増大を招きます。

## なぜ調整が必要か

kが小さいと関連情報を見逃してしまい、不正確な回答やハルシネーションにつながります。kが大きいとコンテキスト窓を圧迫し、LLMが無関係な情報に引きずられる「lost in the middle」問題が起こります。最適なkはクエリの種類・チャンクサイズ・コンテキスト窓のサイズによって変わります。

## 値域の両端

### 小さすぎると

回答に必要な情報がコンテキストに含まれず、LLMが自身の知識のみで回答します。グラウンディングが不十分になり、ハルシネーションリスクが増大します。複数文書にまたがる質問に対応できません。

### 大きすぎると

コンテキスト窓の大部分を検索結果が占め、指示やシステムプロンプトの影響力が相対的に低下します。トークンコストが線形に増加し、レイテンシも悪化します。無関係なチャンクがノイズとなり、かえって回答品質が下がります。

## 決め手となるフォース

- `[F4]` レイテンシ予算 — kの増加はプロンプト長の増加を通じてレイテンシに直結する
- `[F7]` コスト感度・スケール — 投入トークン数がコストに直結する

## 目安（出発点）

- 一般的なQ&A: top-k 5〜10
- 複雑な分析・比較: top-k 10〜20
- チャンクサイズが大きい場合（1000トークン超）: kを小さめに
- リランカー併用時: 初期取得を多め（k=50〜100）にし、リランク後に5〜10に絞る

## 調整の実務

- Recall@kを評価データセットで計測し、kを増やしても改善しなくなる点を見つける
- リランカーを導入し、初期取得は広め・最終投入は絞る二段構成を検討する
- チャンクサイズとkの組み合わせを最適化する（小チャンク×多k vs 大チャンク×少k）
- コンテキスト窓使用率を監視し、検索結果が窓の50%を超えないようにする
