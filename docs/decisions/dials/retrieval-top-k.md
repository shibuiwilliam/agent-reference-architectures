# 検索 top-k / 投入量

!!! abstract "一言"
    RAGで取得するチャンク数を制御し、情報の網羅性とコンテキスト溢れのバランスを取る。

## 概要

検索拡張生成（RAG）において、ベクトル検索やハイブリッド検索から取得する上位k件のチャンク数。kが大きいほど関連情報を取りこぼす確率は下がるが、LLMに投入するコンテキストが膨らみ、トークンコスト増加・注意の希薄化・レイテンシ増大を招く。

## なぜ調整が必要か

kが小さいと関連情報を見逃し、不正確な回答やハルシネーションの原因になる。kが大きいとコンテキスト窓を圧迫し、LLMが無関係な情報に引きずられる「lost in the middle」問題が発生する。最適なkはクエリの種類・チャンクサイズ・コンテキスト窓のサイズによって変わる。

## 値域の両端

### 小さすぎると

回答に必要な情報がコンテキストに含まれず、LLMが自身の知識のみで回答する。グラウンディングが不十分になり、ハルシネーションリスクが増大する。複数文書にまたがる質問に対応できない。

### 大きすぎると

コンテキスト窓の大部分を検索結果が占め、指示やシステムプロンプトの影響力が相対的に低下する。トークンコストが線形に増加し、レイテンシも悪化する。無関係なチャンクがノイズとなり、かえって回答品質が下がる。

## 決め手となるフォース

- `[F4]` レイテンシ予算 — kの増加はプロンプト長の増加を通じてレイテンシに直結する
- `[F7]` コスト感度・スケール — 投入トークン数がコストに直結する

## 目安（出発点）

- 一般的なQ&A: top-k 5〜10
- 複雑な分析・比較: top-k 10〜20
- チャンクサイズが大きい場合（1000トークン超）: kを小さめに
- リランカー併用時: 初期取得を多め（k=50〜100）にし、リランク後に5〜10に絞る

## 調整の実務

- Recall@kを評価データセットで計測し、kを増やしても改善しなくなる点を見つける
- リランカーを導入し、初期取得は広め・最終投入は絞る二段構成を検討する
- チャンクサイズとkの組み合わせを最適化する（小チャンク×多k vs 大チャンク×少k）
- コンテキスト窓使用率を監視し、検索結果が窓の50%を超えないようにする
