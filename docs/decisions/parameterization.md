# パターンのパラメータ化

!!! abstract "一言"
    パターンは定数でなく、駆動変数を引数に最適点を返す**関数**として扱う。

## パラメータ化とは

アーキテクチャパターンを「適用する/しない」の二値で扱うと、過剰適用か適用不足のどちらかに陥る。実際には、パターンは **駆動変数 `[F#]` を引数に受け取り、具体的な設計パラメータを返す関数** である。

```
設計パラメータ = f(F1, F2, …, F9)
```

この考え方を「パターンのパラメータ化」と呼ぶ。

## 具体例

### 例1: #2 Durable Agent Session のチェックポイント頻度

[#2 Durable Agent Session](../patterns/01-execution/02-durable-agent-session.md) は状態を永続化するパターンだが、「どの頻度でチェックポイントを取るか」はパラメータである。

- `[F1]` 可逆性が**低い**（不可逆な副作用が多い）→ **毎ステップ**でチェックポイント
- `[F1]` 可逆性が**高い**（全ステップやり直し可）→ **N分間隔**で十分
- `[F7]` コスト感度が**高い** → I/Oを減らすため間隔を広げる

つまり `チェックポイント頻度 = f(F1, F7)` であり、F1 が低いほど頻度を上げ、F7 が高いほど頻度を下げる。両方高い場合はトレードオフの判断が必要になる（→ [相反の選定基準](tradeoffs.md)）。

### 例2: #32 Agent Trace のサンプリング率

[#32 Agent Trace](../patterns/07-observability/32-agent-trace.md) は全ステップをログに残すパターンだが、本番で100%記録するとストレージコストが爆発する。

- `[F8]` 説明責任が**高い**（規制業種）→ サンプリング率 **100%**（全件記録が義務）
- `[F8]` が**低い** + `[F7]` コスト感度が**高い** → **1–10%** に抑える
- 異常検知時のみ100%に引き上げる動的サンプリングも選択肢

### 例3: #37 Semantic Gateway のルーティング閾値

[#37 Semantic Gateway](../patterns/08-cost-scaling/37-semantic-gateway-cost-aware-router.md) は難易度に応じてモデルを振り分けるが、「どの閾値で大モデルに回すか」がパラメータである。

- `[F7]` コスト感度が**高い** → 閾値を**上げて**大モデル利用を減らす
- `[F3]` リクエスト価値が**高い** → 閾値を**下げて**品質を優先する

## パラメータ化の作法

1. **パラメータを特定する**: パターンの「調整（程度）」節に記載されたダイヤルがパラメータ候補（→ [程度ダイヤル](tuning-dials.md)）
2. **駆動変数を紐づける**: 各パラメータに影響する `[F#]` を特定する
3. **目安値を設定する**: フォースの「高/中/低」に応じた出発点を決める
4. **計測と調整のループを回す**: 本番メトリクスを見て値を更新する
5. **根拠を記録する**: なぜその値にしたかを設計文書やトレースに残す（→ [#32 Agent Trace](../patterns/07-observability/32-agent-trace.md)）

## パラメータ化しないリスク

目盛りの根拠を残さないまま「なんとなく」で設定すると、以下の問題が起きる。

- **チューニング不能**: 問題が起きても何を変えればよいか分からない
- **属人化**: 設定の意図が担当者の頭にしかない
- **過剰/過少適用**: フォースが変化しても設定が追従しない

これ自体がアンチパターンであり、[アンチパターン集](../anti-patterns.md) の「目盛りの根拠を残さない」に該当する。

## まとめ

パターンを導入するときは、「このパターンのパラメータは何か」「どのフォースで決まるか」「現在の値と根拠は何か」を明示する。この3点が揃って初めて、パターンは運用可能な設計判断になる。
