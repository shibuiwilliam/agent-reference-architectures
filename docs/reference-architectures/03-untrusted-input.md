# 3. 信頼できない入力構成

!!! abstract "一言"
    不特定ユーザーの入力を安全に処理するための、境界防御と権限分離を中心にした6層構成。

## このアーキテクチャが必要になるとき

エージェントを社外に公開する場面です。不特定多数のエンドユーザーが自然言語で自由に入力できます。当然、入力にはプロンプトインジェクション、PII（個人情報）の混入、意図的な悪用が含まれる可能性があります。

SaaSのチャットサポート、公開APIとして提供するAIアシスタント、消費者向けアプリのAI機能など、`[F5]` 入力の信頼度が低い状況が幅広く対象になります。社内ツールであっても、利用者が数百人を超えると入力の多様性は急激に増し、事実上「信頼できない入力」と同じように扱う必要が出てきます。

この構成の核心は「入力を信頼しない」という前提に立つことです。信頼できない入力を受け入れつつシステム全体への影響を最小化するために、境界での検査・LLMの権限分離・被害半径の制限を多層的に組み合わせます。

## 構成パターン一覧

| 層 | パターン | 役割 | なぜ必要か |
|---|---------|------|-----------|
| 境界 | [#13 Natural Language Boundary Adapter](../glossary.md) | 入力の構造化 | 自然言語のままLLMに渡すと、指示と入力の境界が曖昧になりインジェクションが通りやすくなります |
| 検査 | [#42 Data Boundary Firewall](../glossary.md) | PII/インジェクション検査 | 入力に含まれるPIIや悪意のあるプロンプトを事前に検出・除去しないと、下流で漏洩や誤動作が起きます |
| 分離 | [#44 Dual-LLM Privilege Separation](../glossary.md) | 隔離LLMと特権LLMの分離 | ユーザー入力を処理するLLMと、ツール実行権限を持つLLMを分離しないと、インジェクションで直接ツールが操作されます |
| 権限 | [#18 Least-Privilege Tool Binding](../glossary.md) | 最小権限 | 全ツールにフルアクセスを与えると、被害が際限なく広がります |
| 被害限定 | [#43 Confused-Deputy Damage Limitation](../glossary.md) | 被害半径の制限 | 権限を最小化しても、残った権限の範囲で被害が出えます。操作レートや影響範囲に上限を設けます |
| ガードレール | [#29 Guardrail Sidecar + Self-Correction](../glossary.md) | 出力検査 | 入力だけでなく出力にも検査が必要です。攻撃者が出力を通じて情報を抜き出す手法があります |

## 各層の詳細

### 境界層 — Natural Language Boundary Adapter

ユーザーの自然言語入力を、構造化されたフォーマット（意図・エンティティ・パラメータ）に変換します。これにより、下流のLLMに渡す「データ」と「指示」の境界を明確にします。この層がないと、ユーザー入力がシステムプロンプトと混ざり、インジェクション攻撃の主要な攻撃面になります。

### 検査層 — Data Boundary Firewall

入力と出力の両方を検査し、PII（個人情報）の漏洩、既知のインジェクションパターン、機密データの混入を検出します。検出ルールはパターンマッチと分類モデルの組み合わせが一般的です。この層がないと、ユーザーが意図せず含めたクレジットカード番号や、攻撃者が仕込んだインジェクション文字列がそのままLLMに到達します。

### 分離層 — Dual-LLM Privilege Separation

ユーザー入力を直接扱う「隔離LLM」と、ツール実行権限を持つ「特権LLM」を分離します。隔離LLMはユーザーの意図を解釈するだけで、外部APIやデータベースへのアクセス権を持ちません。特権LLMは隔離LLMの構造化された出力のみを受け取ります。この層がないと、巧妙なインジェクションで攻撃者がツールを直接操作できてしまいます。

### 権限層 — Least-Privilege Tool Binding

エージェントに公開するツールを、タスクに必要な最小限に絞ります。たとえば「顧客情報の参照」だけが必要なエージェントに「顧客情報の削除」権限を与えません。この層がないと、万一の侵害時に攻撃者が利用できるツールの範囲が不必要に広がります。

### 被害限定層 — Confused-Deputy Damage Limitation

最小権限を設定しても、残った権限の範囲で被害は発生しえます。この層では、操作のレート制限、1回の操作で影響するレコード数の上限、金額の上限などを設けます。この層がないと、権限範囲内であっても大量のデータ削除や高額決済が一度に実行されるリスクがあります。

### ガードレール層 — Guardrail Sidecar + Self-Correction

LLMの出力を検査し、機密情報の漏洩、不適切なコンテンツ、ポリシー違反がないかを確認します。違反が検出された場合は出力を差し替えるか、自己修正を試みます。この層がないと、入力側の防御を突破された場合に最後の砦がありません。

## 省略してよいもの・追加を検討するもの

- **省略可**: 入力元が限定的で、かつ認証済みの社内ユーザーのみの場合は、Dual-LLM分離を簡略化できます（ただし完全な省略は推奨しません）
- **追加検討**: マルチテナント環境では [#41 Tenant-Isolated Agent Runtime](../glossary.md) でテナント間の隔離を追加します。副作用を含む場合は[副作用重視構成](02-side-effect-first.md)のSaga・承認層を重ねます

## 具体的なシナリオ

BtoCのSaaSが提供するAIチャットサポートを考えます。エンドユーザーは月間数万人です。自然言語で製品の質問、契約変更の依頼、不具合の報告を行います。

ユーザーの入力はまずNatural Language Boundary Adapterで構造化されます。「契約を解約したい。クレジットカード番号は1234-5678-...」という入力は、意図=「解約」、PII検出=「クレジットカード番号あり」と分解されます。Data Boundary Firewallがクレジットカード番号をマスクし、インジェクションチェックを通します。

構造化された意図はDual-LLMの隔離LLMに渡ります。隔離LLMは「解約リクエスト」と判断し、構造化された出力を特権LLMに送ります。特権LLMはLeast-Privilegeで「契約参照」「解約申請作成」のみのツールにバインドされており、「全契約一括削除」のようなツールにはアクセスできません。Confused-Deputy Damage Limitationにより、1回のセッションで処理できる解約は1件に制限されます。最終的な応答はGuardrail Sidecarで検査され、内部システムの情報が漏れていないことを確認してからユーザーに返されます。
