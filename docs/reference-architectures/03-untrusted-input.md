# 3. 信頼できない入力構成

!!! abstract "一言"
    不特定ユーザーの入力を安全に処理するための、境界防御と権限分離を中心にした6層構成。

## このアーキテクチャが必要になるとき

エージェントを社外に公開する。不特定多数のエンドユーザーが自然言語で自由に入力できる。このとき、入力にはプロンプトインジェクション、PII（個人情報）の混入、意図的な悪用が含まれうる。

SaaSのチャットサポート、公開APIとして提供するAIアシスタント、消費者向けアプリのAI機能など、`[F5]` 入力の信頼度が低い状況全般が対象である。社内ツールであっても、利用者が数百人を超えると入力の多様性は急激に増し、事実上「信頼できない入力」と同等に扱う必要が出てくる。

この構成の核心は「入力を信頼しない」という前提に立つことである。信頼できない入力を受け入れつつ、システム全体への影響を最小化するために、境界での検査・LLMの権限分離・被害半径の制限を多層的に組み合わせる。

## フォース評価

| フォース | 評価 | この構成での意味 |
|---------|------|----------------|
| `[F1]` 可逆性 | 中 | 入力に起因する被害を限定する必要がある |
| `[F2]` 失敗コスト | 中〜高 | インジェクション攻撃が成功すると情報漏洩につながりうる |
| `[F3]` 1リクエストの価値 | 低〜中 | 大量のリクエストを捌く場面が多い |
| `[F4]` レイテンシ予算 | 中 | 検査レイヤーを通すため多少のオーバーヘッドは許容 |
| `[F5]` 入力の信頼度 | 低 | 不特定ユーザーの自然言語入力 |
| `[F6]` タスクの変動性 | 中〜高 | ユーザーの意図が多様 |
| `[F7]` コスト感度 | 中 | セキュリティのための追加呼び出しはコストより優先 |
| `[F8]` 説明責任 | 中 | セキュリティインシデント時の追跡が必要 |
| `[F9]` プロバイダ信頼度 | — | セキュリティとは直接関係しない |

## 構成パターン一覧

| 層 | パターン | 役割 | なぜ必要か |
|---|---------|------|-----------|
| 境界 | [#13 Natural Language Boundary Adapter](../patterns/03-io-contract/13-natural-language-boundary-adapter.md) | 入力の構造化 | 自然言語のままLLMに渡すと、指示と入力の境界が曖昧になりインジェクションが通りやすい |
| 検査 | [#42 Data Boundary Firewall](../patterns/09-security/42-data-boundary-firewall.md) | PII/インジェクション検査 | 入力に含まれるPIIや悪意のあるプロンプトを事前に検出・除去しないと、下流で漏洩や誤動作が起きる |
| 分離 | [#44 Dual-LLM Privilege Separation](../patterns/09-security/44-dual-llm-privilege-separation.md) | 隔離LLMと特権LLMの分離 | ユーザー入力を処理するLLMと、ツール実行権限を持つLLMを分離しないと、インジェクションで直接ツールが操作される |
| 権限 | [#18 Least-Privilege Tool Binding](../patterns/04-tools-mcp/18-least-privilege-tool-binding.md) | 最小権限 | 全ツールにフルアクセスを与えると、被害が際限なく広がる |
| 被害限定 | [#43 Confused-Deputy Damage Limitation](../patterns/09-security/43-confused-deputy-damage-limitation.md) | 被害半径の制限 | 権限を最小化しても、残った権限の範囲で被害が出うる。操作レートや影響範囲に上限を設ける |
| ガードレール | [#29 Guardrail Sidecar + Self-Correction](../patterns/06-reliability/29-guardrail-sidecar-self-correction.md) | 出力検査 | 入力だけでなく出力にも検査が必要。攻撃者が出力を通じて情報を抜き出す手法がある |

## 各層の詳細

### 境界層 — Natural Language Boundary Adapter

ユーザーの自然言語入力を、構造化されたフォーマット（意図・エンティティ・パラメータ）に変換する。これにより、下流のLLMに渡す「データ」と「指示」の境界を明確にする。この層がないと、ユーザー入力がシステムプロンプトと混ざり、インジェクション攻撃の主要な攻撃面になる。

### 検査層 — Data Boundary Firewall

入力と出力の両方を検査し、PII（個人情報）の漏洩、既知のインジェクションパターン、機密データの混入を検出する。検出ルールはパターンマッチと分類モデルの組み合わせが一般的である。この層がないと、ユーザーが意図せず含めたクレジットカード番号や、攻撃者が仕込んだインジェクション文字列がそのままLLMに到達する。

### 分離層 — Dual-LLM Privilege Separation

ユーザー入力を直接扱う「隔離LLM」と、ツール実行権限を持つ「特権LLM」を分離する。隔離LLMはユーザーの意図を解釈するだけで、外部APIやデータベースへのアクセス権を持たない。特権LLMは隔離LLMの構造化された出力のみを受け取る。この層がないと、巧妙なインジェクションで攻撃者がツールを直接操作できてしまう。

### 権限層 — Least-Privilege Tool Binding

エージェントに公開するツールを、タスクに必要な最小限に絞る。たとえば「顧客情報の参照」だけが必要なエージェントに「顧客情報の削除」権限を与えない。この層がないと、万一の侵害時に攻撃者が利用できるツールの範囲が不必要に広がる。

### 被害限定層 — Confused-Deputy Damage Limitation

最小権限を設定しても、残った権限の範囲で被害は発生しうる。この層では、操作のレート制限、1回の操作で影響するレコード数の上限、金額の上限などを設ける。この層がないと、権限範囲内であっても大量のデータ削除や高額決済が一度に実行されるリスクがある。

### ガードレール層 — Guardrail Sidecar + Self-Correction

LLMの出力を検査し、機密情報の漏洩、不適切なコンテンツ、ポリシー違反がないかを確認する。違反が検出された場合は出力を差し替えるか、自己修正を試みる。この層がないと、入力側の防御を突破された場合に最後の砦がない。

## 省略してよいもの・追加を検討するもの

- **省略可**: 入力元が限定的で、かつ認証済みの社内ユーザーのみの場合は、Dual-LLM分離を簡略化できる（ただし完全な省略は推奨しない）
- **追加検討**: マルチテナント環境では [#41 Tenant-Isolated Agent Runtime](../patterns/09-security/41-tenant-isolated-agent-runtime.md) でテナント間の隔離を追加する。副作用を含む場合は[副作用重視構成](02-side-effect-first.md)のSaga・承認層を重ねる

## 具体的なシナリオ

BtoCのSaaSが提供するAIチャットサポートを考える。エンドユーザーは月間数万人。自然言語で製品の質問、契約変更の依頼、不具合の報告を行う。

ユーザーの入力はまずNatural Language Boundary Adapterで構造化される。「契約を解約したい。クレジットカード番号は1234-5678-...」という入力は、意図=「解約」、PII検出=「クレジットカード番号あり」と分解される。Data Boundary Firewallがクレジットカード番号をマスクし、インジェクションチェックを通す。

構造化された意図はDual-LLMの隔離LLMに渡る。隔離LLMは「解約リクエスト」と判断し、構造化された出力を特権LLMに送る。特権LLMはLeast-Privilegeで「契約参照」「解約申請作成」のみのツールにバインドされており、「全契約一括削除」のようなツールにはアクセスできない。Confused-Deputy Damage Limitationにより、1回のセッションで処理できる解約は1件に制限される。最終的な応答はGuardrail Sidecarで検査され、内部システムの情報が漏れていないことを確認してからユーザーに返される。
