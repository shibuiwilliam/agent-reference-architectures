# 5. コスト重視構成

!!! abstract "一言"
    大量リクエストを低コストで処理するための、ルーティング・キャッシュ・努力配分を組み合わせた6層構成。

## このアーキテクチャが必要になるとき

プロトタイプの段階ではLLMのAPI料金をそれほど気にしなくて済みますが、ユーザー数が増えて月間数万〜数十万リクエストを処理するようになると話が変わります。1リクエストあたりのコストが小さくても、積み重なれば月間コストは急激に膨らみます。

典型的には、BtoCアプリのAIチャット機能、社内全社員向けのナレッジ検索、大量の文書を処理するバッチジョブなどが該当します。いずれも `[F7]` コスト感度が高く、1リクエストあたりの価値（`[F3]`）は比較的低い状況です。

この構成の考え方は「すべてのリクエストに同じ計算資源を投じない」ことです。簡単な質問は軽量モデルで、類似の質問はキャッシュで、難しい質問だけ高性能モデルで処理します。努力の配分を適応的に行うことで、品質を大きく落とさずにコストを抑えられます。

## フォース評価

| フォース | 評価 | この構成での意味 |
|---------|------|----------------|
| `[F1]` 可逆性 | 高 | 回答の誤りは再生成で対応できる |
| `[F2]` 失敗コスト | 低〜中 | 個々のリクエストの失敗は致命的ではない |
| `[F3]` 1リクエストの価値 | 低 | 大量リクエストを低単価で処理する |
| `[F4]` レイテンシ予算 | 中 | キャッシュヒット時は高速、ミス時は多少の遅延を許容 |
| `[F5]` 入力の信頼度 | 中〜高 | コスト最適化とセキュリティは直交する |
| `[F6]` タスクの変動性 | 低〜中 | 類似のリクエストが繰り返される |
| `[F7]` コスト感度 | 高 | 月間コスト上限が厳しい、またはリクエスト量が多い |
| `[F8]` 説明責任 | 低 | コスト最適化が主目的で監査要件は低い |
| `[F9]` プロバイダ信頼度 | 中〜高 | 複数モデルを使い分けるため、フォールバック先の確保が重要 |

## 構成パターン一覧

| 層 | パターン | 役割 | なぜ必要か |
|---|---------|------|-----------|
| ルーティング | [#37 Semantic Gateway & Cost-Aware Router](../decisions/dials/model-tier-routing.md) | 難易度別モデル振り分け | 全リクエストを高性能モデルで処理するとコストが線形に増えます |
| キャッシュ | [#38 Semantic Result Cache](../decisions/dials/cache-similarity.md) | 類似クエリの再利用 | 同じような質問が繰り返される場合、LLMを呼ぶ必要がありません |
| プロンプト | [#39 Prompt Cache Optimized Context](../foundations/forces/f7-cost-sensitivity.md) | prefix共有でキャッシュ | システムプロンプトやコンテキストの共通部分をキャッシュし、入力トークン料金を削減します |
| 努力配分 | [#56 Adaptive Effort](../foundations/forces/f7-cost-sensitivity.md) | 難易度で計算量調整 | 簡単な質問に長いChain-of-Thoughtを走らせるのは無駄です |
| 予算 | [#5 Time-Budgeted Agent Loop](../decisions/dials/budget-cap.md) | リクエスト単位の上限 | 予算なしだと暴走したリクエストが全体の予算を食い潰します |
| フォールバック | [#40 Fallback & Graceful Degradation](../decisions/tradeoffs-catalog/fail-fast-vs-degradation.md) | 障害時の縮退 | 高性能モデルが障害のとき、全リクエストが失敗するのを防ぎます |

## 各層の詳細

### ルーティング層 — Semantic Gateway & Cost-Aware Router

リクエストの内容を分析し、難易度や種類に応じて適切なモデルに振り分けます。FAQ的な質問は軽量・安価なモデルに、複雑な推論が必要な質問は高性能モデルに送ります。この層がないと、「今日の天気は？」のような質問にも最高性能モデルを使うことになり、コスト効率が極端に悪化します。

### キャッシュ層 — Semantic Result Cache

意味的に類似したクエリの回答をキャッシュから返します。完全一致ではなく埋め込みベクトルの類似度で判定するので、表現が違うだけの質問にもヒットします。この層がないと、「Pythonのインストール方法」と「Pythonをインストールするには」が別リクエストとして毎回LLMを呼ぶことになります。キャッシュのTTL（有効期限）とヒット率のバランス調整が運用の鍵です。

### プロンプト層 — Prompt Cache Optimized Context

システムプロンプトやRAGで取得したコンテキストの共通部分を、LLMプロバイダのプロンプトキャッシュ機能で再利用します。prefix部分を固定し、ユーザー固有の部分だけを変えることで、入力トークンの課金を大幅に削減できます。この層がないと、毎リクエストで同じシステムプロンプトのトークン料金が発生します。

### 努力配分層 — Adaptive Effort

リクエストの難易度を事前に推定し、計算量（推論ステップ数、ツール呼び出し回数など）を適応的に調整します。簡単な質問はゼロショットで即答し、難しい質問のみChain-of-ThoughtやReActループを走らせます。この層がないと、全リクエストに同じ計算量を投じることになり、簡単な質問で無駄なコストが発生します。

### 予算層 — Time-Budgeted Agent Loop

リクエスト単位でLLM呼び出し回数・トークン数・実行時間に上限を設けます。予算を超えそうになったら、途中結果を返すか、低コストモデルにフォールバックします。この層がないと、1件の暴走リクエストが月間予算の大部分を消費する事故が起きえます。

### フォールバック層 — Fallback & Graceful Degradation

高性能モデルのAPI障害時やレート制限到達時に、代替モデルやルールベースの回答にフォールバックします。完全な回答が返せなくても、「ただいま回答品質が低下しています」と告知しつつ部分的な回答を返す方が、エラー画面を見せるよりずっとよいユーザー体験になります。この層がないと、プロバイダの障害が直接サービスの全面停止につながります。

## 省略してよいもの・追加を検討するもの

- **省略可**: リクエスト量が少ない（月間数千件以下の）段階ではSemantic CacheやPrompt Cache Optimized Contextの効果が薄いです。ルーティング層だけ先行導入する手もあります
- **追加検討**: `[F2]` が高まったら[副作用重視構成](02-side-effect-first.md)の安全層を重ねます。`[F9]` が高まったら [#45 Agent Runtime Abstraction](../decisions/tradeoffs-catalog/build-vs-buy.md) でプロバイダ間の切り替えを容易にします

## 具体的なシナリオ

社内1,000人が使うナレッジ検索AIを考えます。月間リクエスト数は10万件です。社内Wiki、Confluence、Google Driveの内容をRAGで検索し、回答を返します。月間のLLM API予算は50万円です。

Semantic Gatewayがリクエストを受け取り、分類します。「社内カフェテリアの営業時間は？」のような定型的な質問（全体の40%）は、軽量モデル（GPT-4o miniクラス）に振り分けます。Semantic Result Cacheが過去の類似回答をチェックし、ヒット率30%で即座に返します。これだけで全体の58%のリクエストがLLMの本格的な呼び出しなしに処理されます。

残りの42%のリクエストに対して、Adaptive Effortが難易度を推定します。単純なRAG検索で答えられるもの（25%）はゼロショットで回答し、複数ドキュメントの横断分析が必要なもの（17%）のみマルチステップ推論を実行します。Time-Budgeted Agent Loopが各リクエストに上限を設け、暴走を防ぎます。高性能モデルのAPI障害時は、Fallbackが軽量モデル＋「回答品質が通常より低い可能性があります」の注記で代替します。

この構成により、全リクエストを高性能モデルで処理する場合と比べて、月間コストを60〜70%削減できる見込みです。

## 発展パス

- `[F2]` が高まったら → [副作用重視構成](02-side-effect-first.md)の安全層を追加します（ナレッジ検索からアクション実行に発展する場合）
- `[F8]` が高まったら → [継続改善運用構成](06-continuous-improvement.md)でコスト削減が品質に影響していないかを評価します
- `[F9]` が高まったら → [#45 Agent Runtime Abstraction](../decisions/tradeoffs-catalog/build-vs-buy.md) と [#46 Model Behavior Compatibility Layer](../decisions/tradeoffs-catalog/single-vs-multi-provider.md) でマルチプロバイダ運用を強化します
- キャッシュヒット率が低下したら → [#24 Context Pack / Assembly](../decisions/tradeoffs-catalog/rag-vs-finetuning.md) でコンテキストの構造を最適化します
