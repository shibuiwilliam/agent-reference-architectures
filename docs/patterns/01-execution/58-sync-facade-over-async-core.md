# #58 Sync Facade over Async Core｜同期ファサード

!!! abstract "一言"
    短時間で終わるリクエストは同期レスポンスで返し、閾値を超えたら自動的に非同期ジョブへ昇格させる。

## 概要

すべてのリクエストを非同期にすると、すぐ返せるものまでポーリングやWebSocket接続が必要になりUXが煩雑になる。逆にすべて同期にすると、長い処理でコネクションタイムアウトが起きる。このパターンでは同期ファサードが処理を開始し、閾値時間内に完了すればそのままレスポンスを返す。超えそうになったらバックグラウンドジョブに昇格し、`202 Accepted + job_id` を返して非同期モードに切り替える。

## 設計

```mermaid
flowchart TD
    Req[リクエスト受信] --> Start[処理開始]
    Start --> Timer{閾値内に完了?}
    Timer -->|Yes| Sync["200 + 結果を返却"]
    Timer -->|No| Promote["ジョブ昇格<br/>202 + job_id"]
    Promote --> Q[(Job Queue)]
    Q --> W[Agent Worker]
    W -->|完了通知| Client[SSE / Polling]
```

閾値は設定可能にし、ファサード内部ではタイマーと処理を並行して走らせる。昇格時には進行中の状態をそのままワーカーに引き継ぐ（プロセス間なら [#2 Durable Agent Session](02-durable-agent-session.md) 経由）。

## 解決する課題

`[F4]` レイテンシ予算の観点で、ユーザーは「すぐ返るものはすぐ欲しいが、長いものは待てる」という二面的な期待を持つ。一律のAPI設計ではどちらかを犠牲にする。このパターンはクライアントに最適なUXを提供しつつ、バックエンドの非同期アーキテクチャ `[F1]` の耐久性も維持する。

## 向き / 不向き

- **向き**: 同一エンドポイントに軽いクエリと重い処理が混在するAPI。チャットボットの応答（単純な挨拶は同期、調査タスクは非同期）。
- **不向き**: 処理時間が常に一定（すべて短い、またはすべて長い）の場合。クライアントが非同期モード専用に設計されている場合は [#1 Request-to-Job Gateway](01-request-to-job-gateway.md) で十分。

## 要素技術

- ファサード: FastAPI + asyncio.wait_for、Next.js API Routes + AbortController
- 昇格: 閾値超過時にセッション状態をシリアライズしてキューへ投入
- クライアント: `202` 受信時にポーリングまたはSSEに自動切り替えするSDK / フロントエンドロジック

## 調整（程度）

- **同期待機の閾値** — 短すぎると多くのリクエストが非同期化しUXが煩雑 ⇔ 長すぎるとコネクション占有・タイムアウトリスク / 決め手 `[F4]` / 目安: 5〜10秒。CDNやロードバランサのタイムアウト設定も考慮。→ [程度ダイヤル](../../decisions/tuning-dials.md)

## 選定（相反）

- **同期 ↔ 非同期** — 処理時間の分布が閾値をまたぐ場合にこのパターンが有効。処理時間が安定して短い／長いなら一方に寄せる `[F4]`。→ [相反の選定基準](../../decisions/tradeoffs.md)
