## 概要

たとえば、問い合わせ対応用のエージェントにデータベースの削除権限やインフラ変更用のツールまで見えていたら、プロンプトインジェクション一発で取り返しのつかない操作が実行されかねない。ツール数が増えるほど、こうした「使う予定のないツールが呼ばれてしまう」事故のリスクは増大する。

本パターンでは、セッション開始時にタスク種別・ユーザー権限・コンテキストに基づいて、利用可能なツールセットを動的に絞り込む。エージェントから見ると「存在しないツールはそもそも呼べない」ため、攻撃面と事故の影響範囲を構造的に縮小できる。

!!! info "意思決定上の位置づけ"
    - **必要にするフォース**: `[F5]` 入力の信頼度・`[F2]` 失敗コスト
    - **関与する決定**: [程度（ダイヤル）](../../decisions/tuning-dials.md) の 露出ツール数
    - **意思決定の進め方**: [意思決定の進め方](../../decisions/decision-flow.md)

## 設計

セッション開始時に Binder がユーザーのロール、タスク種別、リスクレベルを評価し、ツールカタログから該当セッションで許可するツールだけを抽出してエージェントに注入する。セッション途中でツールを追加する場合は、あらためて再評価を経る必要がある。

権限の粒度はツール単位にとどまらず、ツール内のパラメータ制約（たとえば `delete` は禁止し `read` のみ許可するなど）まで含めることができる。

## 解決する課題

「全ツール公開」にすると、エージェントの選択肢が爆発してツール選択の精度が下がるとともに、被害の影響範囲も拡大してしまう。`[F5]` インジェクション攻撃で高権限ツールが呼ばれるリスクを構造的に排除し、`[F2]` 誤操作時の被害を限定するのがこのパターンの狙いである。

## 向き / 不向き

- **向き**: ツール数が多い（10以上）システムや、マルチテナント環境に適している。権限レベルが異なるユーザーが同一エージェントを共用する場合に特に有効である。
- **不向き**: ツールが2〜3個で全ユーザーが同権限のシンプルな構成では過剰になりやすい。また、動的にツールを発見しながら進める探索的タスクにも向かない。

## 要素技術

- MCP の `tools/list` フィルタリング
- ツールカタログ + RBAC / ABAC エンジン
- セッションスコープのツールセット注入（LLM の system prompt / tools パラメータ制御）
- OPA / Cedar によるポリシー評価
