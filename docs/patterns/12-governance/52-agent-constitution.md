# #52 Agent Constitution｜エージェント憲法

!!! abstract "一言"
    エージェントの行動原則・禁止事項・優先順位を体系的に定義し、全エージェントに一貫して展開する。

## 概要

個々のエージェントにシステムプロンプトで「やるな」「気をつけろ」とアドホックに書くと、エージェント間で行動基準がばらつき、抜け漏れが発生する。Agent Constitutionは組織レベルの行動原則――倫理規定、データ取扱い方針、エスカレーション条件、禁止操作――を構造化した文書として定義し、全エージェントのシステムプロンプトやガードレールに自動的に注入する仕組みを提供する。

!!! info "意思決定上の位置づけ"
    - **必要にするフォース**: `[F8]` 説明責任・規制・`[F2]` 失敗コスト
    - **意思決定の進め方**: [意思決定の進め方](../../decisions/decision-flow.md)

## 設計

Constitutionは階層構造を持つ:

1. **組織レベル**: 全エージェント共通の原則（データ保護方針、倫理規定、法令遵守）
2. **ドメインレベル**: 業務領域固有のルール（金融なら適合性原則、医療なら診断禁止等）
3. **エージェントレベル**: 個別エージェントの行動制約（操作範囲、権限上限）

各レベルの原則はYAML / JSON等の機械可読形式で管理し、バージョン管理する。デプロイ時にテンプレートエンジンがシステムプロンプトに注入し、[#30 Policy-as-Code Guardrail](../06-reliability/30-policy-as-code-guardrail.md) のルールとしても展開する。

## 解決する課題

エージェントが組織の方針に反する行動を取った場合、「誰がどのルールを設定したか」が不明確だと責任の所在が曖昧になる `[F8]`。アドホックなプロンプト修正の積み重ねは、矛盾や抜け漏れを生む。体系的な原則定義により、行動基準の一貫性と変更の追跡可能性を確保する。失敗コストが高い領域ほど、明文化された原則の価値は大きい `[F2]`。

## 向き / 不向き

- **向き**: 複数エージェントを運用する組織。規制産業（金融・医療・法務）。行動原則の監査証跡が必要なケース。
- **不向き**: 単一エージェントの実験段階で、原則がまだ固まっていない初期フェーズ（まず動かして学ぶ段階）。

## 要素技術

- 原則定義: YAML / JSON / Markdown でバージョン管理（Git）
- 注入: テンプレートエンジン（Jinja2等）でシステムプロンプトに合成
- 実施: [#30 Policy-as-Code Guardrail](../06-reliability/30-policy-as-code-guardrail.md) でランタイム検証
- 監査: 変更履歴をGitログ + 監査ストアに記録
