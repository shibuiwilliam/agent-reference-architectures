# #26 Forgetting and Expiration｜忘却・失効

!!! abstract "一言"
    記憶に**TTL（生存期間）と鮮度スコア**を付与し、古くなった情報を自動で失効・削除する。

## 概要

長期メモリに情報を蓄積し続けると、古い事実が新しい事実と矛盾し、エージェントの判断品質が低下する。Forgetting and Expiration は、すべての記憶エントリに有効期限または鮮度メトリクスを設定し、期限切れのエントリを検索結果から除外するか物理削除する仕組みを導入する。「忘れる」ことを設計上の機能として扱い、記憶の衛生を維持する。

    - **意思決定の進め方**: [意思決定の進め方](../../decisions/decision-flow.md)

## 設計

記憶エントリには以下のメタデータを付与する。

- **TTL**: 作成時に設定する絶対有効期限（例: 90日）
- **鮮度スコア**: 参照されるたびに更新し、長期間未参照のエントリはスコアが減衰
- **上書きフラグ**: 同一キーの新しい記憶が書き込まれた場合に旧版を無効化

失効処理はバッチ（日次の掃除ジョブ）またはクエリ時フィルタ（検索時にTTL超過を除外）で実装する。規制要件でデータ保持期間が定められている場合 `[F8]` は、TTLをその期間に合わせ、削除ログを監査証跡として残す。

## 解決する課題

忘却機能がないと、次の問題が蓄積する。(1) 古い製品仕様・価格・規制解釈が「正しい記憶」として参照され続ける。(2) 記憶の総量が膨張し、検索精度が低下する（ノイズ増加）。(3) GDPR等のデータ保持規制に違反するリスクが生じる。人間の記憶と同様に「適切に忘れる」ことが、最新性と法令遵守の両方に必要となる。

## 向き / 不向き

- **向き**: 顧客情報の継続管理、ニュースや市場データなど鮮度が重要な領域、GDPR/個人情報保護法の対象システム。
- **不向き**: 法的保存義務のある記録（忘却ではなくアーカイブが必要）、変化しない参照データ（マスタデータ等）。

## 要素技術

- TTL管理: Redis TTL、DynamoDB TTL、PostgreSQL パーティションプルーニング
- 鮮度減衰: アクセスログベースのスコアリング、指数減衰関数
- 削除ジョブ: cron / Cloud Scheduler によるバッチ削除
- 監査: 削除ログの保持（何を・いつ・なぜ削除したか）

## 調整（程度）

- **TTLの長さ** — 短すぎると有用な記憶も消える、長すぎると古い情報がノイズに / 決め手 `[F8]` / ドメインの情報鮮度に合わせる。→ [程度ダイヤル](../../decisions/tuning-dials.md)
