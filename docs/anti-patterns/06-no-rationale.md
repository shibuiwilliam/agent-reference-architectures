# 6. 目盛りの根拠を残さない

!!! abstract "一言"
    タイムアウト値やリトライ回数、ガードレール閾値を「なんとなく」で設定し、根拠を記録しないまま本番に投入してしまうアンチパターン。

## よくある場面

あるチームが半年前にデプロイしたエージェントで障害が発生しました。タイムアウトが15秒に設定されていますが、なぜ15秒なのか誰も説明できません。当時の担当者は異動しており、設計ドキュメントにも記載がありません。「10秒にすべきか、20秒にすべきか」という議論が始まりますが、判断材料がないため結論が出ません。

結局「安全のために30秒にしよう」という妥協案で変更し、これが別の問題（コネクション占有）を引き起こしました。リトライ回数やガードレール閾値も同様に「最初に誰かが決めた値」がそのまま残っており、システムの成長とともに不整合が広がっていきます。

## 症状

- パラメータの値に対して「なぜその値か」を説明できる人がいません
- 障害時に「どのパラメータを変えればよいか」の判断が遅れます
- パラメータ変更がその場しのぎで行われ、副作用を生みます
- 新メンバーが設定値の意図を理解できず、変更を恐れます
- 類似システムで異なるパラメータ値が使われていますが、理由が不明です

## 根本原因

パラメータの値を決めること自体に注力し、「なぜその値か」の記録を怠ります。コードレビューでは実装の正しさは確認されますが、設定値の妥当性や根拠は見過ごされやすいです。また、パラメータ値はコード内にハードコードされることが多く、変更の経緯がコミットログに埋もれてしまいます。

駆動変数 `[F#]` とパラメータの対応関係が明示されていないため、状況が変わった（ユーザー数の増加、モデルの変更など）ときに、どのパラメータを見直すべきかが分かりません。

## 発見方法

- **パラメータ棚卸し**: 全設定パラメータを一覧化し、各値について「なぜこの値か」を記述できるか確認します
- **ADRの有無**: アーキテクチャ決定記録（ADR）にパラメータの根拠が記載されているか確認します
- **変更履歴の追跡**: パラメータ変更のコミットメッセージに理由が書かれているか確認します
- **チェック**: 新メンバーに設定ファイルを見せて「この値は何に基づいているか」を聞きます

## 対策

### ステップ1: パラメータと駆動変数の対応表を作成する

各パラメータが依存する `[F#]` を明記し、駆動変数が変化したときに影響を受けるパラメータを逆引きできるようにします。

### ステップ2: ADRにパラメータの根拠を記録する

パラメータの初期値、それを決めた根拠（駆動変数の値、負荷テスト結果、ベンチマーク等）、および変更時の条件を記録します。

### ステップ3: 設定値にコメントで根拠を残す

```yaml
# 設定ファイルにインラインで根拠を記述
timeout:
  sync_request: 10s
  # 根拠: P99レイテンシ 3s（2024-01測定）の3倍 + マージン
  # 駆動変数: [F4] レイテンシ予算 = ユーザー向けUI、10s超で離脱率急増
  # 見直し条件: モデル変更時、トラフィック2倍増時
  # ADR: docs/adr/003-timeout-policy.md

retry:
  max_attempts: 3
  # 根拠: LLMプロバイダの一時障害率 0.1%（2024-01実績）
  # 駆動変数: [F9] プロバイダ信頼度 = 高（SLA 99.9%）
  # 3回で十分カバー（1-(0.001^3) ≒ 99.9999%）
```

## 具体例

### Before（問題のある状態）

```python
# マジックナンバーが散在
TIMEOUT = 15          # なぜ15？
MAX_RETRIES = 5       # なぜ5？
GUARDRAIL_THRESHOLD = 0.6  # なぜ0.6？
TOP_K = 10            # なぜ10？
```

### After（改善後）

```python
# パラメータを構造化し、根拠と紐づける
AGENT_CONFIG = {
    "timeout_seconds": 10,        # ADR-003: [F4] P99=3s x 3倍 + マージン
    "max_retries": 3,             # ADR-004: [F9] SLA 99.9% → 3回で十分
    "guardrail_threshold": 0.85,  # ADR-005: [F5][F2] 偽陽性率1%以下
    "retrieval_top_k": 5,         # ADR-006: [F7] 品質ピーク k=5（評価結果）
}
```
