# [C9] 挙動変更＝モデル更新

!!! abstract "一言"
    コード変更なしにモデル更新で挙動が変わる——従来のCI/CDの変更検知では捉えられない回帰が発生します。

## 概要

従来のソフトウェアでは挙動変更はコードの変更を伴い、diffとテストで検知できました。AIエージェントでは、プロバイダがモデルを更新するだけで出力の品質・形式・傾向が変わります。自社のコード、プロンプト、設定ファイルはすべて同一のまま、しかしサービスの挙動だけが変わるという事態が起きます。Gitのコミット履歴を見ても原因は見つかりません。

## なぜ問題になるか

プロバイダが「gpt-4o」のマイナーバージョンを更新し、JSON出力のフォーマットが微妙に変わります。下流のパーサーが壊れ、エラー率が急増するが、デプロイは一切行っていないため原因特定に時間がかかります。別のケースでは、モデル更新で回答のトーンが変わり、顧客満足度スコアが低下します。評価CI/CDを回していないチームは「いつから品質が下がったか」すら把握できません。モデルの旧バージョンが非推奨化され、数週間後に使えなくなるという通知を見落とし、突然の障害になることもあります。

## 従来ソフトウェアとの比較

| 観点 | 従来のソフトウェア | AIエージェント |
|------|-------------------|---------------|
| 挙動変更のトリガー | 自社のコード変更（diff追跡可能） | プロバイダのモデル更新（自社diff無し） |
| 変更の検知 | CI/CDのテスト＋コードレビュー | 評価パイプラインでの統計的検知が必要 |
| ロールバック | 前バージョンのコードをデプロイ | モデルバージョンの固定＋プロンプト調整 |
| 変更の影響範囲 | 変更したコードのパスのみ | 全リクエストに影響しうる |

## 影響を受けるフォース

- `[F8]` 説明責任・規制 — 挙動変更を検知・記録できないと監査要件を満たせない
- `[F9]` プロバイダ信頼度 — プロバイダの更新頻度や事前通知の質がリスクを左右する
- `[F2]` 失敗コスト — モデル更新による品質低下が事業に直結する場合、バージョン固定が必須

## 防波堤となるパターン

- [#33 Version Pinning](../../glossary.md) — プロンプト・モデル・ツールのバージョンを固定し、意図しない変更を防ぐ
- [#35 Production Replay](../../glossary.md) — 本番ログを新モデルで再生し、旧モデルとの差異を検出する
- [#36 Shadow / Canary Deployment](../../glossary.md) — モデル更新を段階的に投入し、問題があれば自動ロールバックする
