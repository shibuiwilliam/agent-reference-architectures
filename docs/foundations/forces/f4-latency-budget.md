# [F4] レイテンシ予算（Latency Budget）

!!! abstract "一言"
    ユーザーがどれだけ待てるかを測るフォース。予算が小さいほど同期処理・キャッシュ・軽量モデルが必須になり、大きいほど品質に振れます。

## 概要

ユーザーがチャット欄に文字を打つたびに補完候補を出すなら100ms以内に返す必要があるが、週次のリサーチレポートなら翌朝までに仕上がれば十分です。この「どれだけ待てるか」の幅が、選べるアーキテクチャの選択肢を根本的に決めます。

レイテンシ予算は、リクエストの発行から結果の受領までにユーザーが許容する時間の長さを表します。

## なぜ重要か

レイテンシ予算を見誤ると、ユーザーは結果を待ちきれず離脱するか、逆にシステムは不必要に品質を犠牲にします。LLM呼び出しは数百ms〜数十秒を要するため、同期HTTPの枠に収まらないケースが多いです。予算超過はHTTPタイムアウト、コネクション切断、ユーザー体験の崩壊に直結します。

## 値域の解釈

### 低い場合

即応（100ms〜数秒）を期待される状況。検索サジェスト、チャットの1ターン応答、リアルタイムの分類・フィルタリングなどが該当します。LLMの生呼び出しでは間に合わないことが多く、キャッシュ、軽量モデル、ストリーミング出力、またはLLMを使わない従来手法への切り替えが求められます。

### 高い場合

数分〜数時間の待機を許容できる状況。リサーチレポート生成、コードベース全体のリファクタリング、大規模データ分析などが典型例。非同期ジョブとして受け付け、進捗通知を返しながらバックグラウンドで処理できます。品質向上のためのマルチステップ推論やアンサンブルにも予算を割けります。

## 評価の指針

- ユーザーが結果を待つUIか、バックグラウンドで完了通知を受けるUIか
- 現行の類似機能で許容されている応答時間はどの程度か
- 処理中にストリーミングで中間結果を返せばユーザーの体感待ち時間を短縮できるか
- ロードバランサやAPIゲートウェイのタイムアウト設定値はいくつか
- SLAやSLOで応答時間の上限が定められているか
