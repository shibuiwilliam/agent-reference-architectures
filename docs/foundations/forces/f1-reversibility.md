# [F1] 可逆性（Reversibility）

!!! abstract "一言"
    失敗したときに「やり直せるか」を測るフォース。不可逆な副作用が多いほど、防御的な設計が必須になります。

## 概要

エージェントが誤って顧客に見積もりメールを送信してしまった——データベースのレコードならロールバックできるが、送ったメールは取り消せません。この「やり直しがきくかどうか」が、アーキテクチャに求められる安全策の厚みを大きく左右します。

可逆性は、エージェントが起こした副作用を事後に取り消せる度合いを表します。この差がアーキテクチャに要求する安全策の厚みを決めます。

## なぜ重要か

可逆性を無視して設計すると、エージェントのハルシネーションやツール誤呼び出しが**取り返しのつかない結果**を生みます。たとえば、誤った宛先へ契約書メールを送信する、誤った金額で決済APIを叩くといった事故は、事後のログ分析や謝罪では済みません。可逆性が低い操作を含むシステムでは、実行前の検証・承認・ドライランといった構造的な防護層が不可欠になります。

## 値域の解釈

### 低い場合

操作の大半が不可逆な副作用を伴う状況。外部APIへの送信（メール・SMS・Webhook）、金融取引の確定、物理デバイスの制御、法的書類の提出などが該当します。一度実行すると補償トランザクションでしか部分的に取り消せず、その補償自体にもコストがかかります。この領域では Human-in-the-Loop やドライラン優先実行が強く求められます。

### 高い場合

操作が容易にやり直せる状況。社内データベースへの書き込み（トランザクション付き）、ドラフト文書の生成、検索・要約といった読み取り中心のタスクが典型例。失敗してもリトライすればよく、ユーザーへの実害が小さいです。この場合はガードレールを軽量にし、スループットやレイテンシを優先できます。

## 評価の指針

- エージェントが呼び出すツール・APIの中に、実行後に取り消せない操作はあるか
- 補償トランザクション（返金・取消通知など）で被害をどの程度回復できるか
- 誤操作が発覚してから修正までにかかる時間はどれくらいか
- テスト環境やサンドボックスで副作用を模擬実行できるか
- 同じリクエストを複数回実行しても安全か（冪等性が保証されているか）

## 影響する設計判断

### 関連するダイヤル

- [リトライ回数](../../decisions/dials/retry-count.md) — 可逆性が高ければリトライを積極的に設定できます。低ければ0回またはドライラン後のみ
- [自律レベル](../../decisions/dials/autonomy-level.md) — 可逆性が低い操作では自律レベルを下げ、人間承認を挟む
- [チェックポイント頻度](../../decisions/dials/checkpoint-frequency.md) — 不可逆操作の前にチェックポイントを取ることで部分ロールバックを可能にする
- [HITL頻度](../../decisions/dials/hitl-frequency.md) — 可逆性が低いほど承認ゲートを増やす

### 関連する二者択一

- [同期 ↔ 非同期](../../decisions/tradeoffs-catalog/sync-vs-async.md) — 不可逆操作は非同期にして承認待ちを挟みやすくする
- [ワークフロー ↔ エージェント](../../decisions/tradeoffs-catalog/workflow-vs-agent.md) — 不可逆ステップが多いほどワークフロー寄りの制御が安全
- [インライン検証 ↔ 事後検証](../../decisions/tradeoffs-catalog/inline-vs-post-verification.md) — 可逆性が低ければインライン（実行前）検証を優先

## 関連パターン

- [#4 Agent Saga](../../glossary.md) — 不可逆な副作用連鎖を補償トランザクションで巻き戻す
- [#19 Dry-Run First Tool Execution](../../glossary.md) — 副作用をまず模擬実行し、承認後に本実行する
- [#31 Human Approval Checkpoint](../../glossary.md) — 高リスク操作の前に人間の承認を得る
- [#57 Autonomy Ladder](../../glossary.md) — 実績に応じて自律性を段階的に昇格させる
- [#16 Ambiguity Negotiation](../../glossary.md) — 曖昧な指示で不可逆操作を実行しないよう確認を挟む

## 関与する具体構造

| # | パターン | 一言 | 向き |
|---|---------|------|------|
| #1 | **Request-to-Job Gateway** | 1リクエストを非同期ジョブとして受け付ける | マルチステップの調査・コンテンツ生成・分析など、数秒〜数分かかるタスク |
| #2 | **Durable Agent Session** | 状態を永続化し中断・再開に耐える | マルチステップの研究・コード生成・データパイプライン、ローリングデプロイ環境 |
| #4 | **Agent Saga** | 副作用連鎖を補償で巻き戻す | 複数外部システムへの書き込み連鎖（カレンダー→チケット→メール） |
| #16 | **Ambiguity Negotiation** | 曖昧なら確認してから実行 | 可逆な操作、複数解釈可能な入力（ファイル削除）、スロット不足の入力 |
| #19 | **Dry-Run First Tool Execution** | 副作用はまず模擬実行→承認 | データ変更（削除・API書き込み）、インフラ変更（Terraform的操作） |
| #31 | **Human Approval Checkpoint** | 高リスク前に人間承認 | 金融、インフラ変更、顧客メール送信、契約確認 |
| #57 | **Autonomy Ladder** | 実績に応じ自律性を段階的に昇格 | エージェント権限の段階的ロールアウト、タスク種別ごとにリスクレベルが異なる |
| #58 | **Sync Facade over Async Core** | 短ければ同期、超えたら非同期へ昇格 | 軽い挨拶と重い調査が同じエンドポイントに混在するハイブリッドワークロード |
