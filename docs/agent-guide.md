# コーディングエージェント向け利用ガイド

!!! abstract "一言"
    本カタログをコーディングエージェントが読み込み、AIエージェントを含むソフトウェアアーキテクチャを**根拠付きで**人間に提案するための手順・規約・出力様式。

## このガイドの目的

本カタログ（59パターン・9フォース・20ダイヤル・16二者択一・6リファレンスアーキテクチャ）は、人間向けのリファレンスであると同時に、**コーディングエージェントが設計提案を生成するための構造化データソース**として設計されている。

このガイドでは、コーディングエージェントが本カタログを**どう取り込み、どう使い、何を出力すべきか**を定義する。

---

## 取り込み方法

トークン予算に応じて3つの経路から選択する。

### 経路1: 索引→必要な詳細のみ取得（推奨）

1. `/llms.txt` を読み、カタログの全体構造を把握する
2. `/catalog.json` を読み、構造化データ（フォース・ダイヤル・二者択一・パターン・規則）を取得する
3. 必要なパターンの詳細のみ、個別の `.md` ページを取得する

### 経路2: 意思決定コアのみ（低トークン）

1. `/llms-core.txt` を読む（フォース＋ダイヤル＋二者択一＋リファレンスアーキ＋規則＋早見表）
2. 詳細が必要なパターンのみ個別取得

### 経路3: 全文一括（コンテキストに余裕がある場合）

1. `/llms-full.txt` を読み、全ページを一括取り込む

### 経路4: MCP接続（ネイティブ統合）

MCP サーバを接続し、会話中に必要な情報を都度取得する。

- `search_patterns(query)` — 意味検索でパターン候補
- `get_pattern(id)` — 構造化詳細
- `recommend(force_profile)` — フォース評価→推奨パターン
- `list_reference_architectures()` — 複合構成一覧
- `get_decision(dial|tradeoff)` — ダイヤル/二者択一の詳細

---

## 設計手順

要件を受け取ったら、以下の手順でアーキテクチャ提案を生成する。

### ① フォース評価（F1–F9）

9つの駆動変数を「高/中/低」で見積もる。根拠を必ず添える。

| フォース | 問い |
|---------|------|
| F1 可逆性 | 失敗をやり直せるか |
| F2 失敗コスト | 金銭/法務/安全の痛み |
| F3 1リクエストの価値 | 売上/意思決定への寄与 |
| F4 レイテンシ予算 | ユーザーの待機耐性 |
| F5 入力の信頼度 | 攻撃/汚染の混入可能性 |
| F6 タスクの変動性 | 定型↔探索 |
| F7 コスト感度・スケール | QPS・月間コスト上限 |
| F8 説明責任・規制 | 監査・コンプラ要件 |
| F9 プロバイダ信頼度 | 外部LLMの可用性 |

### ② 二者択一を解く

フォース評価に基づき、16の二者択一（同期↔非同期、シングル↔マルチエージェントなど）の方向を決定する。`catalog.json` の `tradeoffs` セクションの `driver` と `default` を参照。

### ③ ダイヤルを設定する

採用パターンに関連する20のダイヤルの初期値を、フォースの値域から決める。`catalog.json` の `dials` セクションの `driver` と `default` を参照。

### ④ パターンを選定し、複合構成に組む

- `catalog.json` の `rules` を参照し、フォース条件に合致する推奨パターンを取得する
- リファレンスアーキテクチャ（6構成）との対応を確認する
- 必要に応じてパターンを追加・省略する

### ⑤ 提案を出力する

必ず[アーキテクチャ提案テンプレート](agent-proposal-template.md)に従って出力する。

## 引用規約

提案に含めるすべての判断に、カタログの安定IDを**根拠として明記**する。

- パターン: `#N`（例: `#31 Human Approval Checkpoint`）
- フォース: `[F#]`（例: `[F2]` 失敗コスト）
- ダイヤル: ダイヤル名（例: `タイムアウト`）
- 二者択一: 二者択一名（例: `同期↔非同期`）
- リファレンスアーキテクチャ: 構成名（例: `副作用重視構成`）

**例**: 「`[F2]` が高く `[F1]` が低いため、`#31 Human Approval Checkpoint` と `#19 Dry-Run First` を採用し、`副作用重視構成` をベースに構成する」

---

## 境界規約（安全規約）

!!! warning "必ず遵守"

1. **カタログ内パターンのみ使用**: 本カタログに定義された59パターン・20ダイヤル・16二者択一のみを提案の語彙として使う。**カタログに存在しないパターンを捏造しない**。
2. **不確実性の開示**: フォース評価が曖昧な場合、該当パターンの適用可否が不明な場合は、**「不確実」と明示**し、人間に確認を求める。
3. **最終判断は人間**: 提案は**人間レビュー前提**であり、自動適用を前提としない。提案テンプレートの「未解決の論点」セクションで、人間に確認したいことを明記する。
4. **網羅性の限界**: 本カタログは「AIエージェントの本番アーキテクチャ」に関するパターン集であり、万能ではない。**カタログの範囲外の設計判断**（データベース選定、ネットワーク設計など）については、その旨を明示する。
5. **目安値は出発点**: ダイヤルの目安値やデフォルトは「出発点」であり、本番データでの検証と調整が前提。断定的な数値指定を避ける。

---

## カタログのバージョン

提案には `catalog.json` の `version` を明記する（例: `v1.0.0`）。バージョンが変わるとパターンの追加・変更がありうるため、引用の再現性のために必要。
