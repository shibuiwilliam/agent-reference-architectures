# コーディングエージェント向け利用ガイド

!!! abstract "一言"
    コーディングエージェントが本カタログを読み込んで、AIエージェントのアーキテクチャを**根拠付きで**人間に提案するための手順・規約・出力様式をまとめたガイドです。

!!! note "リポジトリを直接読み込むエージェントへ"
    リポジトリをローカルに持つエージェントは、このページの代わりに [`_agent/README.md`](https://github.com/shibuiwilliam/agent-reference-architectures/blob/main/_agent/README.md) を起点にしてください。`_agent/` ディレクトリには、段階的開示・タスク別/問題別インデックス・手続き的決定アルゴリズム・Few-Shot例など、ローカルアクセスに最適化されたファイル群があります。このページは Web 経由でアクセスするエージェント向けの手順書です。

## このガイドの目的

本カタログ（59パターン・9フォース・20ダイヤル・16二者択一・6リファレンスアーキテクチャ）は、人間向けのリファレンスであると同時に、**コーディングエージェントが設計提案を生成するための構造化データソース**でもあります。

このガイドでは、カタログの取り込み方、使い方、出力すべきフォーマットを定めます。

---

## 取り込み方法

トークン予算に応じて、以下の経路から選べます。

### 経路1: 索引→必要な詳細のみ取得（推奨）

1. `/llms.txt` を読み、カタログの全体構造を把握する
2. `/catalog.json` を読み、構造化データ（フォース・ダイヤル・二者択一・パターン・規則）を取得する
   - `by_force` フィールド: フォースIDからパターン・ルール・ダイヤル・二者択一を逆引きするインデックス
   - `selection_guide` フィールド: フォース評価の組み合わせからリファレンスアーキテクチャ候補を引くガイド
3. 必要なパターンの詳細は `/glossary/`（早見表）または各意思決定ページを参照する

### 経路2: 意思決定コアのみ（低トークン）

1. `/llms-core.txt` を読む（フォース＋ダイヤル＋二者択一＋リファレンスアーキ＋規則＋早見表）
2. 詳細が必要なパターンは `glossary.md` または各意思決定ページを参照

### 経路3: 全文一括（コンテキストに余裕がある場合）

1. `/llms-full.txt` を読み、全ページを一括取り込む

### 経路4: MCP接続（ネイティブ統合）

MCP サーバを接続し、会話中に必要な情報を都度取得します。

- `search_patterns(query)` — 意味検索でパターン候補
- `get_pattern(id)` — 構造化詳細
- `recommend(force_profile)` — フォース評価→推奨パターン
- `list_reference_architectures()` — 複合構成一覧
- `get_decision(dial|tradeoff)` — ダイヤル/二者択一の詳細

## 設計手順

要件を受け取ったら、以下の手順でアーキテクチャ提案を生成します。

### ① フォース評価（F1–F9）

catalog.json の `forces[]` を参照します。各フォースの `question` に対して要件を照合し、高/中/低を判定します。根拠を必ず添えてください。

| フォース | 問い |
|---------|------|
| F1 可逆性 | 失敗をやり直せるか |
| F2 失敗コスト | 金銭/法務/安全の痛み |
| F3 1リクエストの価値 | 売上/意思決定への寄与 |
| F4 レイテンシ予算 | ユーザーの待機耐性 |
| F5 入力の信頼度 | 攻撃/汚染の混入可能性 |
| F6 タスクの変動性 | 定型↔探索 |
| F7 コスト感度・スケール | QPS・月間コスト上限 |
| F8 説明責任・規制 | 監査・コンプラ要件 |
| F9 プロバイダ信頼度 | 外部LLMの可用性 |

### ② ルール照合

catalog.json の `rules[]` を走査します。`if` 条件がフォース評価に合致するルールを収集し、`required` / `recommended` / `optional` パターンを得ます。

### ③ 二者択一を解く

catalog.json の `tradeoffs[]` を参照します。各二者択一の `decision_function` にフォース評価を適用し、a / b / hybrid の方向を決定します。

### ④ ダイヤルを設定する

catalog.json の `dials[]` を参照します。各ダイヤルの `value_mapping` にフォース評価を適用し、初期値を決定します。

### ⑤ 構成合成

catalog.json の `architecture_selection` を参照します。フォース条件に合致する base + overlay 構成を決定し、Step 2–3 の結果と組み合わせます。

### ⑥ 提案を出力する

`agent-proposal-template.md` に従い、全判断を根拠付きで出力します。

## 引用規約

提案に含めるすべての判断には、カタログの安定IDを**根拠として添えます**。

- パターン: `#N`（例: `#31 Human Approval Checkpoint`）
- フォース: `[F#]`（例: `[F2]` 失敗コスト）
- ダイヤル: ダイヤル名（例: `タイムアウト`）
- 二者択一: 二者択一名（例: `同期↔非同期`）
- リファレンスアーキテクチャ: 構成名（例: `副作用重視構成`）

**例**: 「`[F2]` が高く `[F1]` が低いため、`#31 Human Approval Checkpoint` と `#19 Dry-Run First` を採用し、`副作用重視構成` をベースに構成する」

## 境界規約（安全規約）

!!! warning "必ず遵守"

1. **カタログ内パターンのみ使用**: 本カタログに定義された59パターン・20ダイヤル・16二者択一のみを提案の語彙として使います。**カタログに存在しないパターンを捏造しないでください**。
2. **不確実性の開示**: フォース評価が曖昧な場合、該当パターンの適用可否が不明な場合は、**「不確実」と明示**し、人間に確認を求めてください。
3. **最終判断は人間**: 提案は**人間レビュー前提**であり、自動適用を前提としません。提案テンプレートの「未解決の論点」セクションで、人間に確認したいことを明記してください。
4. **網羅性の限界**: 本カタログは「AIエージェントの本番アーキテクチャ」に関するパターン集であり、万能ではありません。**カタログの範囲外の設計判断**（データベース選定、ネットワーク設計など）については、その旨を明示してください。
5. **目安値は出発点**: ダイヤルの目安値やデフォルトは「出発点」であり、本番データでの検証と調整が前提です。断定的な数値指定は避けてください。

## カタログのバージョン

提案には `catalog.json` の `version` を書いておきます（例: `v1.2.0`）。バージョンが変わるとパターンの追加・変更がありうるので、引用の再現性に必要です。

---

## アーキテクチャ提案テンプレート

提案は以下の構成で出力してください。詳細は [提案テンプレート](agent-proposal-template.md) を参照。

```
## アーキテクチャ提案 v{catalog_version}
1. 要件と制約の要約
2. フォース評価（C1–9 / F1–9：高/中/低 と根拠）
3. 解いた二者択一（選択・根拠フォース・不採用案）
4. 設定したダイヤル（初期値＝目安・調整方針）
5. 確定した具体構造（パターン #N と採用理由＝効いたフォース）
6. 複合構成（プリセットとの対応）
7. リスクと対応（意思決定の誤り＝アンチパターン）
8. 代替案とトレードオフ
9. 未解決の論点（人間に確認したいこと）
> 本提案はカタログ v{x} に基づきます。最終判断は人間が行ってください。
```
